# brewphase-life-path

一套跨 Agent 的 Skill：借**真实人物的可验证人生路径**来思考自己的人生方向——
从古代到此刻仍在世的人，而不是一句励志语录。

BrewPhase Life Path 不是一个励志故事集，而是一套方法：把你的处境抽象成可检索
的模式，跨地域跨时代找出可比较的人生，核实真实发生过什么，把能迁移的部分和不能
迁移的部分分开，最后给出两三条路线和一件下一步可以做的事。

> English: [README.md](README.md)

---

## 为什么做这个

市面上的「人生建议」工具通常错在三件事上：

1. **样本太窄**：几位美国创业者，被当成普遍规律。
2. **抽掉了条件**：成功被写成「努力 + 相信」，家庭资本、时代窗口、制度支持
   悄悄消失了。
3. **做预测**：给人生附上一个日期，然后让人拿自己跟它比。

这个 Skill 针对这三点设计。覆盖范围明确要求全球化；每个人物档案必须包含
**成立条件**与**付出的代价**；时间一律给区间和假设，不给日期，也不给概率。

## 它会做什么

- 如果你正在跑 BrewPhase Desktop 并授权了 MCP，读取你自己**已确认**的现状、
  方向、阶段与当前工作上下文
- 大范围检索那些**约束条件**与你相似的人，而不是名气和你的野心相似的人
- 用一手资料与学术研究核实事实，并区分「事实」「本人自述」「研究者观点」
  「AI 推断」
- 给出两三条符合你现实条件的路线，附带代价与「失败的早期信号」
- 结尾只给 1–3 个下一步动作，以及一份「暂时不用做」的清单

## 它不做什么

- 不做人格测试，不给相似度百分比（「你和某某 80% 像」）
- 不预测人生结果，不给成功概率
- 不内置人物数据库——每个案例都是使用时现场检索并核实的
- 不改你的 BrewPhase 数据：它只能写**草稿**，需要你在应用内确认
- 不写励志内容，也不拿别人的成就制造焦虑

## 开始使用

### 1.1 用 npx 装

```bash
npx skills add banmu123/BrewPhase
```

适用于遵循 `skills/<name>/SKILL.md` 约定的 Agent。**它到不了 WorkBuddy**，见 1.3。

### 1.2 让 Agent 自己装

把这段贴给 Agent：

> 帮我安装这个 skill：https://github.com/banmu123/BrewPhase
> 读 `skills/brewphase-life-path/references/install.md`，按里面的步骤安装。

那份文件是写给 Agent 看的：它会找 skills 目录、决定用软链还是复制、逐个核对文件
是否到位，并处理可选的那一步 MCP 接入。这条路最不容易出错——Agent 能直接看你机器
上的真实情况，而不是猜。

### 1.3 WorkBuddy

WorkBuddy 从 `~/.workbuddy/skills/`（或 `<workspace>/.workbuddy/skills/`）读 skill。
两条命令，然后重启应用：

```bash
git clone https://github.com/banmu123/BrewPhase ~/BrewPhase
ln -s ~/BrewPhase/skills/brewphase-life-path ~/.workbuddy/skills/brewphase-life-path
```

Windows 上 `ln -s` 需要开发者模式。对应的 PowerShell 写法、不建软链直接复制的做法、
装完怎么验证，以及**怎么接 BrewPhase MCP**（让 skill 能读你自己已确认的方向和工作
上下文），都在 [adapters/workbuddy](adapters/workbuddy/README.md)。

然后用一句应该会命中的话试：

> 我在现在这份工作里待了六年，说不上差，但也不觉得自己在往哪里走。

如果回答里出现几个不同地域、不同时代的人，每个人都有成立条件和代价，说明装好了。
如果只是泛泛的鼓励，说明没加载上——去适配文档的排查表里对一下。

### 1.4 其他 Agent

| Agent | 位置 |
|---|---|
| Codex / `.agents` 约定 | 把这个目录链到你自己仓库的 `.agents/skills/`——见 [adapters/codex](adapters/codex/README.md) |
| Claude Code / 兼容实现 | 把这个目录复制或软链到 `~/.claude/skills/brewphase-life-path` |
| 其他 | 让 Agent 读 `references/install.md` |

装好之后不需要手动点名调用。`SKILL.md` 的 `description` 是按「用户意图匹配」
写的：当对话涉及方向、转型、卡住、想参考某个人物的经历时，Agent 应当自动选中它。

## 用法

装好之后不需要点名调用。用平常的话说出你的处境即可——当问题指向**方向**而不是
某个具体任务时，它会被自动选中。你不需要提某个人、某套框架，也不需要提这个 skill。

### 可以这样问

| 你想做的事 | 可以这样说 |
|---|---|
| 把卡住的状态理清 | 「我在现在这份工作里待了六年，不差，但不知道自己在往哪走。」 |
| 权衡要不要转 | 「我想出来做点自己的东西，但手上只有一年生活费。」 |
| 参考某一类人的经历 | 「在没有正规学历和考试的年代，人是怎么把本事练出来的？」 |
| 判断现不现实 | 「我这种情况，三五年内有可能做到吗？」 |
| 失败之后重建 | 「第一次做砸了，赔了不少。别人是怎么缓过来的？」 |
| 把范围收窄 | 「只看日本的例子，别扯别的国家。」 |

### 会得到什么

一次完整分析的结构是固定的：

1. 你现在在哪，以及真正要问的问题是什么
2. 你想去哪，还有哪部分没说清
3. 4–6 个值得研究的人——每个人的起点、实际做了什么、什么让这件事成立、
   付出了什么、哪部分能迁移、哪部分不能
4. 2–3 条符合你现实条件的路线，每条带代价和「失败的早期信号」
5. 时间以区间给出，分保守/基准/积极三种情景，并说明哪里估不了
6. 1–3 个下一步动作
7. 现在不该做什么，以及什么情况下要重做这次分析

**答案长短跟着问题走。**「我该不该接这份工作」只值四小节；「我不知道这辈子该干
什么」才给完整报告。如果你为一个很小的决定拿到了八个章节，那是 bug，可以直接说。

### 怎么调整它

- *「说短点」*——降到中等或简短形态
- *「只看南亚的人」*——缩小覆盖范围，并说明这样做的分析代价
- *「别讲那些有名的创始人」*——换的是人选，不只是换个说法
- *「直接给下一步」*——跳过研究部分
- *「把这个记成我的方向」*——需要 BrewPhase MCP 的 `direction:propose`；
  它只写**草稿**，要你在应用里确认

### 前提与边界

- **真实研究需要联网检索。** 没有联网时它会明说，并改为提供方法框架——不会假装
  搜过，也不会凭记忆编造出处。
- **BrewPhase 是可选的。** 接上后能读你已确认的现状、方向、阶段与工作上下文；
  不接也能用，只靠对话里说出的话。
- **它不替你做决定。** 它给路线和取舍，选择权在你。它也会拒绝为人生结果给出成功
  概率或完成日期——这是设计，不是可以绕开的限制。

## 可选：接入 BrewPhase

不接也能用——只靠对话里说出的话。若你同时在跑
[BrewPhase Desktop](https://github.com/banmu123/BrewPhase)，可以授权它本地的
MCP bridge，让分析读到已确认的现状、方向、阶段与工作上下文。

前置条件：

- BrewPhase Desktop 在本机运行
- MCP bridge 已开启，并授权了 `direction:read`（读工作上下文还需
  `work_context:read`）
- Scope 由你在应用内授予；没授予的读不到

MCP 是**本地**数据源，不是世界观资料来源。世界人物经历始终由 Agent 自己检索。
详见 [references/brewphase-mcp.md](references/brewphase-mcp.md)。

## 结构

```
brewphase-life-path/
├── SKILL.md                          # 唯一核心入口
└── references/
    ├── coverage-map.md               # 全球覆盖矩阵 + 初始检索锚点
    ├── historical-pattern-matching.md# 五步研究流程
    ├── source-evaluation.md          # 四级证据分级
    ├── personal-analysis.md          # 按「可迁移约束」做匹配
    ├── path-planning.md              # 路线、顺序、下一步
    ├── forecast-guidelines.md        # 区间、情景、不该预测什么
    ├── brewphase-mcp.md              # 读取用户自己的上下文
    ├── response-template.md          # 三种输出体量
    └── install.md                    # 给 Agent 安装用（非运行时）
```

`SKILL.md` 刻意写得短：它只决定**要不要做**和**按什么顺序做**。方法在
references 里，Agent 按需加载，常见场景因此不必背着全部细节。

## 设计约束

这些是让输出保持诚实的硬规则，都写进了 references：

1. **不许编造人生**。缺失可以接受，编造不行。
2. **必须写成立条件与代价**，不能只有结果。
3. **差异与相似同等重要**。
4. 每次完整分析**至少一个反例**——试过没成的人，或成了但付出代价的人。
5. **覆盖下限**：≥2 位历史人物、≥2 位近现代/当代、≥3 个文化背景、
   ≥3 种路径类型。不是同一个国家的四位创始人。
6. **给区间，不给日期**；不给成功概率。
7. **四类陈述不许混**：事实 / 本人自述 / 研究者观点 / 推断。
8. **隐私边界**：用户的材料不进入公共检索，检索只用抽象后的模式。

## 测试

`tests/` 下是人工与评审用的场景规格：

- `trigger-scenarios.md` — 该触发与不该触发
- `coverage-scenarios.md` — 全球与领域覆盖行为

它们是判断标准，不是自动化断言。每个文件里写了怎么执行一次检查。
