## Phase 1.1.2.2：F-1 / F-2 收口（12:41–12:57）

合并前审查（Phase 1.1 Pre-Merge Verification）判 NOT READY，两条文档问题。本轮修完。

**F-1 不是算法问题，是文档写错了方向。** `index = entries.length - max(1, hops)` 本身正确。
旧文档说「过小 → 跳数不足 → 回退 socket」，实测过小取到的是**上游代理 IP**。四象限：

| HOPS 相对真实层数 N | 客户端自带伪造 | 选中值 | 后果 |
|---|---|---|---|
| 偏小 < N | 无关 | 上游代理 IP（不回退 socket） | 同代理后共用一个桶 → 429（fail-closed） |
| 相等 = N | 有 | 客户端真实 IP | 伪造被推到左侧 |
| 偏大 > N | 无 | 条目不足 → 回退 socket | 共用一个桶 → 429（fail-closed） |
| 偏大 > N | 有 | 攻击者自填值 | 每值一个新桶 → **fail-open** |

**只有「偏大且无伪造」才回退 socket。** 1.1.2.1 把这两行混成了「过小=回退 socket」。

**方法要点**：用假 socket 测 `clientIp` 必须伪造 `c.env.incoming.socket.remoteAddress`
（`getConnInfo` 的真实读取路径 = `@hono/node-server/conninfo`）。`app.request` 没有 socket，
回退恒为空串，**无法区分「选中代理 IP」与「回退 socket」**——这是上一轮误判的技术原因。
端到端层面用 `maxAuth=1` + 两个不同取值各发一次即可区分（同桶 429 / 不同桶 401）。
