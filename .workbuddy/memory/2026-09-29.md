### 三条重要结论（都验过）

1. **`.mlpackage` 丢了 `base_score`。** JSON 里是 2.6580412，Core ML 侧按 0.5 算，
   于是每一分都低 2.1580412，未修正时曲线会掉到 −1.08 分（模型文档说范围是 1–5）。
   现在在 `flavor_mapping.json → outputCorrection` 里补回该常数；模型重新导出后必须删掉。
   根因是 `convert_coreml.py` 没传 `base_score`，且它的自检只比对输入名字、不比对数值。
2. **协议 §6.1 的验收对照配错了 bag。** `metrics.json → example_curve` 的 bean_id 是
   `bag_0000`（Gesha/Honey/1937.7/Roaster_09），不是 `predict.py __main__` 那个示例 bag
   （Heirloom/Natural/1800/Roaster_03），拿示例 bag 去对永远对不上。
   另外基准曲线的生成函数 `train.py → canonical_day_rows()` 把开封日写死第 3 天。
   改正之后逐天吻合到 2.6e-6（30 天里 29 天），峰值 14、窗口 [10,19] 与基准一致。
3. **补回 base_score 后第 10 天仍有 0.0126 残差**，只在 `days_since_roast = 10` /
   `days_since_open = 7` 这个整点出现，是转换器的第二处保真问题，只能靠重新转换解决。

### 环境坑（这台机器）

- `sandbox-exec` 完全不可用（连 `/bin/echo` 都 `sandbox_apply: Operation not permitted`），
  而 Xcode 的 `CoreMLModelCompile` / `CoreMLModelCodegen` 都包在 `sandbox-exec` 里，
  所以**只要 `.mlpackage` 在 target 里本机就编不过**。`ENABLE_USER_SCRIPT_SANDBOXING=NO`
  也绕不开。改成随包携带预编译的 `.mlmodelc` + 重编译脚本。
- `xcode-select -p` 虽然指向 Xcode，但 `xcodebuild test` 里仍报
  `unable to find utility "simctl"`；加 `export PATH="$DEVELOPER_DIR/usr/bin:$PATH"` 才稳。
- 本机 Bash 里 `grep` / 重定向写的临时文件不跨调用持久化，验证脚本要用文件工具写。
- 想要 xgboost 做参考计算得先 `brew install libomp`（没装，改走 Core ML 直接实测）。

### 工程既有的红 → 已修好，全量 156 项通过

首轮 10 项失败，在干净检出上同样逐字失败，确认是**测试自身**的问题而不是产品代码：

- `PhaseEngineTests.testOpeningBeforeTheWindowChangesNothing`（8 条）：把「烘焙后第 N 天
  开封」直接传进了 `openedDaysAgo`，而那个参数是**从今天往前数**。于是实际问的是
  第 20/18/15/13 天开封（全都晚于窗口起点），引擎按设计给了顺延。
  **这一类错误的根因是「相对今天的偏移」和「烘焙后第几天」两个坐标混用**——同一个坑
  在 FlavorInputFactory 里也要小心（我用的是绝对的 `openDayAfterRoast`，没这个问题）。
  修法：`openedDaysAgo: 20 - openedOnDay`，并补了另一侧断言（第 8 天开封应当已损失 1 天），
  免得这条测试在折扣完全不生效时也照样通过。
- `NotificationPlannerTests.testABagOpenedLateGetsItsWindowRemindersPushedBack`（2 条）：
  断言 `onTime.map(\.kind) == [.windowEnding]`，但同一文件里
  `testThePriorityNudgeAppearsWhenTheBagCannotBeFinishedInTime` 用**完全相同的参数**
  要求出现 `.brewPriority`。两处自相矛盾，后者是后加的、专门有一节，所以是前者过期。
  修法：按 kind 取 windowEnding 再比，并补一条「按时开封的确实早于晚开封的」断言。

**教训**：同一文件里两个测试用相同输入期望不同结果时，先找出哪个和后加的功能一致，
再改另一个；顺手把「the whole point」写成断言而不是只写在注释里。

### 修掉唯一的并发告警，并摸清了 Swift 6 迁移的底

`LanguageManager.swift:162`：`nonisolated static func pinForTesting` 里读了被
`@MainActor` 隔离的 `static let storageKey`。修法是把常量标成 `nonisolated`——它是不可变的
`String`，本来就没有需要 actor 保护的东西；`nonisolated(unsafe)` 是多余的。

验证方式：`nonisolated` 那条路径不是死代码，`BrewMathTests` / `ConsumptionAndPriorityTests`
的 `setUp` 真的会调 `pinForTesting`，在非主线程上下文里读写 `storageKey` 与 `UserDefaults`，
两个类都通过。默认构建（`SWIFT_STRICT_CONCURRENCY = minimal`）现在 **Swift 告警为零**
（日志里只剩 Xcode 自己的 AppIntents 提示）。

顺手用 `SWIFT_STRICT_CONCURRENCY=complete` 跑了一次全量构建，摸清 Swift 6 迁移面：
**新加的 ML / 卡片 / 工厂代码零告警**，剩下四处既有告警也一并修完了，现在
`complete` 严格并发下**告警归零**，全量 156 项测试仍全过：

- `LanguageManager.swift:53,54` — `languageBundle` / `languageCode` 是无隔离可变全局，
  实际已被 `languageLock` 保护（`currentLocalizedBundle` / `currentLocaleCode` /
  `adoptBundle` 三处都在锁内读写）。标注 `nonisolated(unsafe)` 并写明这个前提。
- `Formatting.swift:134` — `DateFormatterCache.cache` 同理：唯一入口 `formatter(...)`
  开头就 `lock.lock()` + `defer { unlock }`，没有绕过锁的路径。同样 `nonisolated(unsafe)`。
- `ImageStore.swift:11` — 这个**没有**简单注解了事。先查了真实可变状态：三个存储属性
  全是 `let`，没有任何非同步的可变状态；两个引用成员按契约本就线程安全
  （`FileManager` 文档明确多线程安全；`NSCache` 文档明确并发安全，且存进去的 `UIImage`
  不可变）。所以标 `@unchecked Sendable` 是**如实断言**，并在注释里逐个列出这三个属性、
  写明「若将来加了可变存储属性，这个 conformance 必须重新评估」。
- `PhotoFieldView.swift:44` — 根因特别值得记：**`View` 协议本身是 `@MainActor`**
  （SDK 接口原文：`@preconcurrency @_Concurrency.MainActor public protocol View`），
  于是本模块里**所有**自定义 View 类型整体被推成主 actor 隔离；而 `PhotosPicker` 的
  `label:` 参数是 `@Sendable () -> Label`（SDK 接口第 127 行），`@Sendable` 闭包
  **不继承**外层隔离。两者必然冲突。
  修法：把共用的标签抽成 `nonisolated static func actionLabel(...)`——`nonisolated` 抵消
  类型级推断，`static` 顺带避免捕获非 Sendable 的 `self`；里面只构造 `Text` / `Image` /
  `Capsule`，SDK 自己的视图构造器不是隔离的，所以合法。
  **踩坑提示**：把标记代码内联进 `PhotosPicker` 闭包也能过，但要复制十来行样式，会漂移。

排查手法：`grep` SDK 的 `.swiftinterface` 原文看真实隔离声明，比猜快得多。PhotosPicker
在 `_PhotosUI_SwiftUI.framework`，`View` 在 `SwiftUICore.framework`。

**注意**：`SWIFT_STRICT_CONCURRENCY=complete` 是个很有用的体检手段——它能提前把 Swift 6
的硬错误全列出来，而且不必真的切到 Swift 6 语言模式。命令：
`xcodebuild build ... SWIFT_STRICT_CONCURRENCY=complete`。
判据：只要它报零，切 Swift 6 语言模式的隔离面就是干净的。
