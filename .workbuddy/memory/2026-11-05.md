## 记录系统重做：载体 / 标签分离（已完成）

原设计把「到访、视频、文章、开发、灵感、人生」当成六个固定分类，等于让系统替用户
定义内容。这一轮把它们拆成两层：**载体由系统决定（link/image/video/text），意义由
用户用标签赋予**。

### 模型（破坏性改动，但记录从未发布）
- `Record`：`carrierRaw` + 内容（`urlString` / `sourceName` / `previewPath` / `mediaPath`）
  + `title` / `note` + `tags`（多对多）+ 时间。旧的 `kindRaw` / `place` / `imagePath` /
  `link` 已删除。**记录只在这次会话里存在过，没有任何已发布数据受影响**；如果你的
  模拟器里还留着旧 schema 的库，uninstall 重装即可。
- `RecordTag`：独立实体，多对多反向关系 `records`。删除标签只解除关联（有测试钉住）。
  六个建议标签在「既没有标签也没有记录」时铺一次；用户全删了就不会再塞回来。
- `BrewPhaseSchema` 8 → 9。

### 媒体
- `MediaStore`（Application Support/BrewPhase/Media）：视频**只搬文件、只存文件名**，
  绝不进 SwiftData 的字段。封面用 `AVAssetImageGenerator` 取一帧，仍走 `ImageStore`
  （所以备份附件只认 jpg，不会把 .mov 混进去）。
- `PickedVideo: Transferable` 把 PhotosPicker 的临时文件复制成自己的文件。

### 链接
- `LinkPreviewService`：只认 http/https，8 秒超时，页面 ≤1.5MB，抓
  og:title / og:site_name / og:image，退回 `<title>`；属性顺序不敏感（先拆 meta 再查）。
- **永远可选**：抓不到就 `linkFetchFailed`，用户自己填，保存不受影响。
- 输入框防抖 900ms（`.task(id:)` 自动取消上一次）。

### UI
- 添加流程：+ → 添加记录 → **四种载体** → 编辑器（内容 → 你的话 → 标签）→ 保存。
- 记录页：标题 + 搜索（标题/备注/来源/标签）+ 标签筛选（只列用过的标签）+ 四种卡片。
- 标签：编辑器里多选/新建；「管理」进 `TagManagerView` 改名、删除、看用量。
- 卡片底部一行 `标签 · 日期`，标签用 roast 色、不加胶囊，避免抢标题。

### 备份（v3 重新定义）
- `BackupRecord` 换成载体字段 + `tagIDs`；新增 `BackupTag` 与 `BackupData.tags`。
- 恢复时先建标签再挂关系；找不到的标签跳过而不是丢整条记录。
- v2 仍然可读；v3 里没有 `records` 段的文件不动设备上的记录。
- **视频本体不进备份**（可能几百兆，单文件 JSON 装不下）：恢复后记录还在，详情页
  如实显示「这段视频的文件不在本机」。

## 外部链接智能卡片与内嵌播放（已完成）

在「载体归系统、意义归用户」之上，给链接记录加了平台识别、元数据解析与内嵌播放。
核心不变式：**播放地址只由适配器根据内容 ID 现拼**，数据库里永远不存 embed URL，
WebView 也不执行用户输入的任何 HTML。

### 结构
- `Models/LinkMetadata.swift`：LinkProvider / LinkContentKind / LinkEmbedCapability /
  LinkMetadataStatus / LinkFailure + LinkMatch / LinkEmbed / LinkMetadata。
  `LinkMatch` 含 `page`（B 站多 P）与 `canonicalKey`（去重）。
- `Record` 新增平台字段（canonicalURL / providerRaw / contentKindRaw /
  platformContentID / linkPage / authorName / summary / thumbnailURLString /
  metadataStatusRaw + 仓库三件套）。全部**带默认值**，轻量迁移只加列；
  providerRaw 为空的老记录按 URL 现认，卡片不降级。
- 适配器在 `Services/Link/`：YouTube / Bilibili / X / GitHub / Generic，
  统一协议 `LinkProviderAdapter(match/expand/resolve/embed)`，`LinkResolver` 是入口。
  规范化 `LinkURL.cleaned`（去 utm/fbclid/锚点、排序 query、去 www）。

### 播放容器（`Features/Records/ExternalMediaPlayer.swift`）
- WKWebView：inline media、`mediaTypesRequiringUserActionForPlayback = .all`、
  不自动播放、视图销毁时 `loadHTMLString("")` 真停。
- 导航策略：**只有用户点击（linkActivated）才跳出**；越界主框架跳转一律取消
  （B 站 player.html 会 302 到 www.bilibili.com/blackboard/mbplayer.html，
  属于正常站内跳转，允许域 = 平台基域 `bilibili.com`）。
- **包装页**（`parentOrigin`）：YouTube 直接开 /embed/ 无 Referer → 官方错误 153；
  X 帖子组件需要 `width=device-width` 视口否则缩在左上角。固定 iframe 模板 + HTML 转义，
  baseURL = 平台主域；包装页自身的 baseURL 必须放行（否则被自己的白名单拦死）。
- 帖子用白底 + 300pt + 可滚动；视频 16:9 黑底。WebView 底色跟场景走，否则透明区露黑。
- 18 秒 watchdog；全屏是独立 fullScreenCover（退出后行内回封面，避免双声）。

### 环境事实（重要，别再踩）

- `simctl` 不能点击：播放验证用调试开关 `-BrewPhaseForceAutoplay`（放开手势限制 +

## YouTube 152-4 修复：来源身份必须是应用自己（2026-11-05 晚）

- **根因**：包装页 baseURL 伪装成 `https://www.youtube.com/`。YouTube 拒绝
  「自称 YouTube」的嵌入页 → 官方错误 152-4；此外 Privacy Enhanced Mode
  （youtube-nocookie）只适用于网站内嵌，App 内不用。
- **修法**（YouTubeAdapter.embed）：embed URL 改 `https://www.youtube.com/embed/{id}?playsinline=1&rel=0`
  （modestbranding 已被官方废弃，去掉）；`parentOrigin = https://com.brewphase.ios/`
  （Bundle ID 的 https 形式）；allowedHosts 收敛为 `youtube.com`。
  Bilibili（直开 player.html、基域 bilibili.com）与 X（x.com 来源）不动。
- **iframe 加 `referrerpolicy="strict-origin-when-cross-origin"`**；allow 里补 autoplay。
- **验证 Referer 的硬证据**：`decidePolicyFor` 里对子框架导航打
  `iframe referer:` 日志（debug 级），实测发往 YouTube 的 iframe 请求带
  `Referer: https://com.brewphase.ios/`。
- **结果**：jNQXAC9IVRw 与 M7lc1UVf-VE 两个公开视频在模拟器里真实出画（
  force-autoplay 调试路径；三帧 md5 不同证明画面在推进），152-4 消失。
  X 嵌入与 B 站播放器加载均无回归；B 站流 403 是环境限制，与本次无关。
- 调试日志在 `log show` 里要 `--info --debug` 才能看到（默认不持久化 debug 级），
  run.sh 的实时流里直接有。
