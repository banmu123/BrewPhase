## 本机已知环境问题（最重要，下次直接命中）

### 1. 外部宏全部失效 —— `swift-plugin-server produced malformed response`
`@Model` / `@Observable` / `@Query` 一编译就报
`external macro implementation type 'SwiftDataMacros.PersistentModelMacro' could not be found`。
本机 **macOS 15.7.3 + Xcode 26.3（SDK 26.2）**，插件 dylib 存在且能 `dlopen`，
插件服务器二进制也能启动，但它**无法与编译器完成握手**（macOS 版本与新 Xcode 的组合问题，非工程问题）。

**修复**（已写进 pbxproj 的 app / test 各两个 configuration）：

```
OTHER_SWIFT_FLAGS = "$(inherited)
  -plugin-path $(DEVELOPER_DIR)/Platforms/iPhoneOS.platform/Developer/usr/lib/swift/host/plugins
  -load-plugin-library $(DEVELOPER_DIR)/Platforms/iPhoneOS.platform/Developer/usr/lib/swift/host/plugins/libSwiftDataMacros.dylib";
```

要点：
- `-load-plugin-library` 让宏在编译进程内直载，绕开失效的插件服务器；有 / 没有
  `-external-plugin-path` 两种顺序都实测可用。
- 插件目录只存在于 **iPhoneOS.platform**（`iPhoneSimulator.platform` 没有 host plugins），
  模拟器构建也走这一份，所以路径固定写 iPhoneOS.platform 是对的。
- 完整排查步骤见 skill `ios-swiftdata-macro-build-fix`。

### 2. `generic/platform=iOS Simulator` 会编 x86_64
该 destination 下编译切片是 `x86_64`（本机 arm64），且更容易触发上一条。
**必须给具体 destination**：`-destination "platform=iOS Simulator,id=<UDID>"`。

### 3. `xcode-select -p` 指向 CommandLineTools
跑 `xcodebuild` / `xcrun simctl` 前必须 `export DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer`。

### 4. `swift-plugin-server` 会读走 stdin
不要为了「验证它能不能跑」而在脚本里直接执行它：它会读掉脚本剩余的 stdin，
导致后续命令静默不执行（表现为 exit 137 或脚本中断）。要测就加 `</dev/null`。

### 5. pbxproj 批量替换可能只落一部分
同一条消息里对**同一个文件**发多个 Edit，实测出现过只生效其中一处、但两处都报成功的情况。
改完必须复核计数，例如
`grep -c OTHER_SWIFT_FLAGS BrewPhase.xcodeproj/project.pbxproj` 应等于 configuration 数（4）。

## 架构要点（决定后续改动成本）

- **PhaseEngine 是唯一的日期真源**（§30）。输入 `BeanSnapshot` + `PhaseRuleData` + today，
  输出 `PhaseReading`（阶段 / 天数 / 倒计时 / 进度 / 轨道分段）。View 里没有任何日期算术。
  纯函数 ⇒ §31 的边界情况（无烘焙日期 / 未来日期 / 跨月 / 跨年 / 闰年）全是一行测试。
- **§7 表格的正确读法**：`排气期 3–7 天` = 第 3 天前是「太新」、第 3–7 天是「进入窗口」、第 7 天开窗。
  即 `Resting = day < restMinDays`、`Opening = [restMin, peakStart)`。这样四个阶段在每一档默认规则下
  都有真实区间（有测试守着，防止 Opening 退化成永远取不到的词汇）。
  意式拼配 restMax(14) > peakStart(7)，排气期直接并入窗口、不出现 Opening —— 这是刻意设计的。
- **四阶段 + 五词汇**：引擎只有 4 个时间阶段；「建议优先消耗」不是时间点，是
  phase + PriorityTier 推出的结论，由 `PhasePresentation` 负责成词。分数不出引擎。
- **优先级只用于排序**（§17）：分数、理由、档位都算好放进 `PriorityVerdict`，
  UI 只显示 headline + ≤2 条 detail + 一句 closing。养豆期 −40 分，永远排不到第一。
- **Tasting 由 Brew 派生**：保存冲煮记录时，若填了评分/风味/一句话，就顺带插一条
  `source = .brew` 的 Tasting（带 `brewID` 便于精确联动删除）。风味时间轴因此是冲煮的副产品，
  符合「核心操作尽可能少输入」。
- **提醒一次算完**（§10）：`NotificationPlanner` 纯函数算出未来 5 个时间点；
  `NotificationManager` 负责去重（identifier = `brewphase.bean.<uuid>.<kind>`，
  先按全量 identifier 撤销再重建）。**注意**：`UNUserNotificationCenter.add()` 在未授权时
  不抛错也不保留请求（实测），所以 `sync` 必须先查 `isAuthorized`、未授权时不写任何
  `PhaseReminder` 行 —— 否则导出会声称存在永远不会送达的提醒。
- **标签存成 `\u{1F}` 连接的字符串**，不是 `[String]`：规避 SwiftData 可变形
  （transformable）属性的兼容性问题，存取器对外仍暴露 `[String]`。
- **图片**：存两份（≤1400 长边 + ≤400 缩略图），DB 只存文件名；删 Bean 时连图片一起删。
  `ImageStore.image(named:)` 读不到文件返回 nil，不会因为图片缺失而崩溃。

### 为什么之前「构建版本显示正在测试，内测组却说无可用构建版本」

四条各自独立成立的原因（都在本机取到了证据）：

1. **bundle id 换过 ⇒ 两个 ASC App 记录。** 本机 4 个 BrewPhase 归档里，前 3 个是
   `com.brewphase.app`（16:43 / 16:54 / 17:03），第 4 个才是 `com.brewphase.ios`（17:17）。
   构建版本只会出现在与它 bundle id 一致的那条 App 记录下，「正在测试」是旧记录的状态，
   新记录里当然还没有构建。
2. **4 个归档全是 build 1**（BrewPing 的 3 个归档也全是 build 1）。同一 App 的
   同一 (版本, 构建号) 只能上传一次，重复上传被静默拒绝 → 列表里看得到旧的那份，
   新传的从没到过 ASC。
3. **归档里没有出口合规字段** ⇒ 构建状态为「缺少出口合规证明」。苹果官方状态表写明该状态
   在 TestFlight 中**不可见**（内测、外测都不可见），但构建列表里仍会显示它 ——
   这就是「列表看得到、内测组说无可用」的最典型表现。
4. **钥匙串里没有 Apple Distribution 证书**（只有 Apple Development 与 Developer ID
   Application）。上传 App Store Connect 需要分发证书；若上传时未让 Xcode 用 Apple ID
   自动生成，或误用了 Organizer 的 Export（只导出 ipa、不上传），就会出现「以为传了、其实没传」。

## 冲煮页「器具 / 水温」芯片行溢出修复

用户反馈：冲煮记录页的器具、水温候选值「滑出来了」。定位到根因在共享的 `suggestionRow`：

- 用的是 `ScrollView(.horizontal)` + **`.scrollClipDisabled()`**。关了裁剪之后，芯片会画到
  卡片圆角之外、落到页面背景上——这就是「溢出」。同一条 `EditorRow` 的自带发丝线还被
  `.padding(.top, -4)` 拉到芯片底下，形成一条**穿过芯片的横线**。
- 三个候选行（器具 / 粉水比 / 水温）共用这一个 helper，所以一起中招。

改法：不再用横向滚动，改成**换行**。

- `FormComponents.swift` 新增 `EditorChipsRow`：行内「标签 + 输入框」，下面用项目已有的
  `FlowLayout` 铺芯片，自带尾部发丝线；芯片直接用已有的 `SelectableTag`（与同屏的风味标签
  编辑器同一套视觉），并给它 `isOn` —— **当前值对应的芯片会高亮**，这是原来没有的反馈。
- `BrewEditorView` 三处换成 `EditorChipsRow`，删掉 `suggestionRow` / `ratioRow` / 三个
  `*Suggestions` helper。
- 水温芯片改成**裸数字**（86…96），不带 `°C`：行标是「水温」、旁边输入框已经带 `°C`，
  重复七遍只会换来第二行。这样 7 个温标正好一行放得下。
- 粉水比芯片的 `isOn` 直接和 `Fmt.ratio` 的输出做字符串比较（`ratioText == "1:16"`），
  不用另算一遍。

顺带修了同类隐患：`HomeView.tallyRow` 也是「横向 ScrollView + scrollClipDisabled」。
它现在放得下（4 个阶段芯片约贴到 373pt 的内容边界），但更长的文案或更窄的机型就会越界到
页面留白外。改成 `FlowLayout` 换行，只是多一层保险。

`DemoData` 顺手对齐了它自己的文档注释（写着「覆盖每个阶段」但实际没有 Opening 包）：
Colombia Pink Bourbon 从 day(7) 改到 day(5)——浅烘的 Opening 是第 3–6 天，day(7) 已经是 Peak。
现在一次能看到四种阶段状态。

## 已知同类写法（下次别再写）

卡片内不要用「横向 ScrollView + `.scrollClipDisabled()`」铺少量固定候选值：
关了裁剪 = 内容画到容器外。候选值 ≤ 一行放不下时，优先 `FlowLayout` 换行——
项目里 `FlavorTagEditor`、`BeanEditor`、`BeanDetailView` 的元信息行都是这么做的。
