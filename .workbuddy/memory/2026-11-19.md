## Phase 1.3.1-C2b-R1：绑定失败的条件删除

- 两个「绑定不匹配」分支原本都 `deleteAuthRequest(rid)`。同一 rid 允许重新发起
  Provider 登录（换 `provider_state_hash`），于是旧 State 的失配回调会删掉新授权。
- 统一走 `deleteMismatchedProviderRequest()`，六条判据全部取自**那次 SELECT**：
  `id` / `provider_state_hash` / `provider` / 行内 `browser_binding_hash` /
  `provider_consumed_at IS NULL` / `expires_at > now`，`RETURNING id`。
- **命中 0 行 = 状态已变 → 不删、不审计、不重定向**，对外仍 400。审计必须跟着
  条件走：给一个已被新流程取代的 rid 记「绑定劫持」会误导排障。
- `ConsumeOutcome` 的 `binding_mismatch` 改成独立分支，带 `provider` /
  `stateHash` / `storedBindingHash`；`expired` 单独带 `rid`；其余原因不带清理信息。
- 交错测试仍是「外部事务持行锁 → 回调的 DELETE 停锁 → `pg_stat_activity`
  确认在等锁（`wait_event_type='Lock'`）→ 事务内改 State 并提交」。
- **变异脚本的锚点必须唯一**：`deleteDeniedProviderRequest` 与
  `deleteMismatchedProviderRequest` 的 SQL 片段逐字相同，第一次 M1 误改了前者，
  于是「存活」。顺手补了「正常拒绝：旧 State 的拒绝回调也不能删新授权」，
  把 `deleteDeniedProviderRequest` 的 state 判据也钉住。5/5 全抓。

## Phase 1.3.1-C3a：Token Endpoint

- `POST /mcp/oauth/token`（`token-flow.ts`）两分支：`exchangeAuthorizationCode` /
  `exchangeRefreshToken`；独立限流桶 `mcp-token`（不复用浏览器授权那个）。
- **授权码兑换必须单事务**：`sessions.ts` 拆出 `createMcpSessionInTransaction(tx, …)`，
  `createMcpSession()` 退回「事务包装 + 审计」。**不要**先消费码再调
  `createMcpSession()`——中间失败会把码烧掉、Session 没建，用户只能重走浏览器。
- `rotateMcpRefreshToken()` 新增可选 `clientId` / `resource` / `requestedScope`，
  全部在**写任何状态之前**判定；绑定校验必须排在「宽限外重放 → 撤销 Session」
  之前，否则错误 client_id 反而成了破坏性原语。
- `effectiveScope = issued ∩ grant` 先算后写；交集为空 `no_scope` 拒绝且**不消费
  旧代**（消费了客户端就彻底没凭据）。
- 表单解析仍手写 `URLSearchParams`：**任何字段重复即 invalid_request**
  （`Object.fromEntries` 后者覆盖前者 = 校验绕过面）。Token 端点**完全不读**
  `bp_mcp_bs`。
- 非 AppError（drizzle/加密栈）必须在路由层换成固定文案 `serverError()`：
  drizzle message 带整条 SQL 与参数（code_hash、refresh hash 都在里面）。
- 审计走 `auditOrIgnore`（事务外、失败只 warn），不回滚已签发的凭据。

## Phase 1.3.1-C3a-R1：Token 请求体与媒体类型硬化

- 三处请求面问题：`body.length`（UTF-16 码元）当字节、先 `c.req.text()` 再判大小、
  `contentType.startsWith(...)`。全部修在 `cloud/src/routes/mcp-oauth.ts` 的
  `readBoundedBody` / `isFormContentType` / `decodeFormBody`。
- **读法固定**：Content-Length 校验（`/^\d+$/`，**不要用 `Number.isInteger`**——
  `Number("")` 是 0，空头会被当零字节放行）→ 流式累加 `byteLength`（超 8192
  `reader.cancel()`）→ 合并 → `TextDecoder("utf-8", { fatal: true })` → URLSearchParams。
- **顺序不能反**：先截断再解码，否则「超限」与「非法 UTF-8」互相掩盖。
- `app.request()` 会**规范化 header**：`content-type` 的尾随空格会被 undici 去掉，
  所以「尾随空格」这种用例测不到我们的解析层，别写。
- 写这类测试的教训：**必须用「完整合法表单 + 只破坏一个维度」**。半截表单会让
  400 来自「缺 client_id」而不是被测的判据，变异就存活了（M4/M5/M7 第一版全栽在这）。
- 变异 7/7；门禁 Cloud 993 → **1009**（61 files，+16），Desktop 1265 / 89 不变。
- 1 MiB 流式计数用例是「边读边截断」唯一的可观测判据：只断言 400 区分不出
  「读完全部再拒」与「读到 8 KiB 就拒」。

## Phase 1.3.1-C3a-R2：字段限长与 Content-Type 参数唯一性

- **限长必须放在 `parseTokenForm()` 建 Map 的循环里**，不能只放 `requireField()`：
  `scope` 走 `form.get()`、未知扩展字段直接进 Map，两条路都绕过必填校验。
- 错误文案不回显字段名（参数名请求方可控，含换行 → 日志注入面）。
- `isFormContentType` 用 `seen` 集合拒参数重复：`charset=utf-8; charset=UTF-8`
  即使值相同也必须拒——两个解析器各取一个就是两种行为。
- **测试填充构造器的连带坑**：原来用单个 7000 字符的 `pad` 撑 body 测 8 KiB 边界，
  加了字段上限后这些用例会先撞 512 → 改成按目标字节数拼多个 ≤500 字符的字段
  （零头用 `&` 补齐）。否则「8 KiB 边界」测的其实不再是字节维度。
- 变异 3/3；门禁 Cloud 1009 → **1016**（61 files，+7），Desktop 1265 / 89 不变。

## Phase 1.3.1-C3b：Token Revocation（RFC 7009）

- 撤销单位是 **Session**（`mcp_refresh_tokens.session_id → mcp_sessions.id`），
  **不是 Grant**。复用 `revokeMcpSession({reason:"client_revoke"})`，条件更新
  `WHERE revoked_at IS NULL` 保证并发/重复只撤一次、审计只一条。
- **无效 Token 一律 200 空体**（RFC 7009 §2.2）；唯一 400 是有效的 MCP Access JWT
  （`unsupported_token_type`）与请求本身畸形。
- `token_type_hint` 只当提示：**先查 refresh 哈希、未命中才验 JWT**。反过来
  会给攻击者「每个无效 token 换一次签名验证」的 CPU 消耗点。
- 已消费的旧代**不能**撤销它的 Session（否则捡到旧 token 就能踢掉合法会话）；
  Session 已过期**不写** `revoked_at`（过期不是事件，写了审计上分不清）。
- 路由在调用前先判 `getMcpSessionState()`，所以「重复撤销」在 HTTP 层提前返回，
  **测不到** `revokeMcpSession` 自己的条件更新——必须补一条直接打服务层的幂等
  测试，否则 M1/M7 两个变异存活。
- 顺带把 R2 遗留的重复字段文案改成固定串（字段名请求方可控，含换行 → 日志注入）。
- 门禁：Cloud 1016 → **1047**（62 files，+31）；Desktop 1265 / 89 不变；变异 7/7。
