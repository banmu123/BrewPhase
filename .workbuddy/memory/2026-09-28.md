# 2026-09-28

## 国际化（中/英/跟随系统）

给 BrewPhase 加了 App 内语言切换。三条改动线：

### 1. 语言通道

- 新增 `App/LanguageManager.swift`：`AppLanguage`（system / zh-Hans / en）+ **带 NSLock 的全局
  bundle 快照** + `L(_:_:)`。快照做成全局而不是 `@MainActor` 类的属性：通知调度和导出会在非主线程
  构串，读 `@MainActor` 对象编译不过。
- 根视图挂 `.environment(\.locale, …)` + `.id(language.current)`。**tab 选中态提到 `BrewPhaseApp`
  里**（新增 `AppTab`）——否则切语言的整树重建会把用户弹回第一个 tab。
- 同时暴露 `currentLocaleCode()`，让 `Fmt` 用**模板**（`setLocalizedDateFormatFromTemplate`）格式
  化日期，而不是硬编码 `zh_CN`。删掉了 3 处 DatePicker 上的 `.environment(\.locale, zh_CN)`，
  改为继承根视图。

**key 用中文原文**（`"保存" = "Save";`），偏离 skill 里「key 用英文」的默认约定。理由：产品是中文
优先，用可读句子当 key 让源码保持可读、且一句话只有一个出处；`zh-Hans.lproj` 因此是恒等表。
稳定的**标识**（phase/roastLevel 的 rawValue、导出字段名）仍按工程既有约定用英文。

### 2. 真正的坑（详见 skill）

- **组件参数是 `String` = 翻译静默失效**。把只用于显示的参数（`SectionHeader.title`、`EditorRow.title`、
  `EmptyStateView.message`、`EditorTextField.placeholder`…）全改成 `LocalizedStringKey`。调用点写的是
  字面量，**一个都不用改**，编译器还会把所有传 String 变量/三元的位置报出来。
- **裸字面量逃过 `L()`**：`errorMessage = "没能保存下来，请再试一次"` 这种赋值 → `Text(那个变量)` 走
  verbatim。只在错误分支出现，截图审计永远走不到。写了个静态检查（`return`/`=` 右侧的裸中文字面量）
  抓出 4 处真缺陷。
- **`displayName(for:)` 写好了没人调**：风味标签改成「存英文 canonical + 按语言查展示名」后，中文界面上
  出现英文 id。grep 调用点才发现是 0。补了 `displayList(_:limit:)` 统一拼接点，6 个渲染点全部改过去。

### 3. 工具（可复用）

- `Tools/Localization/`：`keys.py`（从源码抽 key）+ `strings.py`（**唯一的翻译表**）+ `generate.py`
  （生成两份 `.strings`）+ `check.py`（6 类校验）+ `audit_screenshots.swift`（Vision OCR 扫英文截图找汉字）。
- `check.py` 做了**故障注入自测**：故意注入「多一个 %@」「删一条译文」「key 重复定义」「真实换行」
  「Swift 里残留插值」「裸赋值」六种故障，逐条确认 exit=1，再确认干净树 exit=0。脚本本身有效才算数。
- `Tools/run.sh` 加 `--lang system|zh-Hans|en`：**装完之后、启动之前**写偏好（install 会清偏好）。
- `audit_screenshots.swift` 要跳过状态栏（Vision 把电池字形稳定读成「今口」），且只把**连续 ≥2 个汉字**
  算失败 —— 单个汉字基本都是 `—`/`★`/chevron 的误读。

**验证**：`plutil -lint` 工程 OK；全量重建后两份 `.lproj` 都在 `BrewPhase.app/` 里；320 key 双语齐全、
占位符个数一致；A/B 交叉验证（系统中文 + App 选 en → 英文界面）通过；10 屏英文 OCR 审计 0 漏译。
工程用的是 `PBXFileSystemSynchronizedRootGroup`，**加 `.lproj` 只需改 `knownRegions`，不需要 PBXFileReference**。

## 赏味期改为参考开封日期（用户反馈「感觉是随机的」）

用户问「赏味期是按真实豆子判断的吗？感觉是随机的」。查证后如实回答：**是确定性的，但只看
`roastDate` + `roastLevel` 两个字段**，`openDate` 存了却从没被 `Core/` 读过。用户选了「让开封日期参与计时」。

实现（用户明确要求**只改代码，测试由他来跑**）：

- `PhaseEngine.sealedDayWeight = 0.5` + `effectiveDay(dayAfterRoast:openDayAfterRoast:rule:)`：
  只对**窗口本该打开之后**封着的那段打折，且**随天数累积**（否则阶段会倒退，且会拿还没挣到的折扣
  去判一包当今还封着的豆子）。半速而不是零：完全不算会让放了三个月的豆子仍显示「黄金窗口」。
- `PhaseReading` 加 `effectiveDay` / `sealedShiftDays`；`dayAfterRoast` 仍是**真实年龄**（UI 照旧显示
  "Day 30"），只有阶段跟着 `effectiveDay` 走。
- `NotificationPlanner.plan` 加 `openDate:`，所有偏移经 `PhaseEngine.dayReaching(_:rule:openDayAfterRoast:)`
  反解 —— 提醒发生在日历日的早上，但说的是阶段钟上的时刻。
- `TastingTimelineView` 改为收 `bean: BeanSnapshot`，让时间轴点的配色和 PhaseCard 用同一套折扣。
- PhaseCard 在 `sealedShiftDays > 0` 时明说原因（「封着的 N 天按半速计入」）—— 不说出来就又是一次
  「看起来随机」。

**过程中发现并修掉一个自己引入的崩溃**：`dayReaching` 里 `max(0, target)...(target + maxDiscount)`
在 target 为负时会构造反向 Range → `Fatal error: Range requires lowerBound <= upperBound`。优先级提醒
那条路径（`peakEnd - estimate.daysRemaining`）就是负数的来源。已改为两端都 clamp。

**仍未验证**（按用户要求没跑测试套件）：新增的 8 个断言（PhaseEngine 6 个 + NotificationPlanner 3 个）
尚未实跑。app target 与 test target 均已 `build` / `build-for-testing` 通过、零警告。

## 产品问题记录：豆种/产地差异不进窗口

用户追问「每种豆子种类和产地庄园都不同的话，赏味期也是一样的吗」。答案：**一样**。
核实：`PhaseEngine` 只读 `roastLevel` / `roastDate` / `openDate`；`PhaseRuleBook.rule(for:)` 只按
`RoastLevel` 查表；`PhaseRuleData` 5 个 case，其中 `mediumDark` 与 `dark` 的**默认数字完全相同**
（1–3 / 3–14 / 14），所以实际只有 4 套不同数字。

已向用户说明并给出判断：**不要按处理法/烘焙商加系数** —— 那是我自己编的权重，会把「随机性」藏进一个
看起来更精确的公式里。真正有价值的两条路：① 允许单包覆盖窗口（模型加两个可选字段 + 编辑界面，小改动，
上一轮我列过但用户选了开封日期那条）；② 以后用用户自己的风味记录反推（需要每包 3+ 条样本）。

风味记录目前只参与两件事：首页「今天建议」排序里的 `lastScore`，以及风味时间轴 —— **不参与阶段**。
