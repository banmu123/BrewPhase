## Desktop 顶部一体化改造（Minimal Integrated Title Bar）

- **问题**：Windows/Linux 是「系统标题栏 + 默认 Electron 菜单栏 + 52px React 顶栏」
  三层叠加（主进程从未 setApplicationMenu，也没有 titleBarOverlay）；
  macOS 已是 hiddenInset 但顶栏 52px。
- **方案**：
  - Windows：`titleBarStyle: 'hidden'` + `titleBarOverlay`（color #f7f8f6 /
    symbol #30372f / height 44）——原生最小化/最大化/关闭画进顶栏右上角，
    Renderer 用 `env(titlebar-area-*)` 预留按钮安全区（实测 137px）；
  - macOS：保持 `hiddenInset`，顶栏左留 80px（原 92px 按 80 校正）；
  - Linux：保留系统标题栏（WCO 各桌面环境行为不一），仅 `autoHideMenuBar`。
  - 菜单：新增 `src/main/app-menu.ts`（role 组装，Ctrl+C/V/Z/A、Ctrl±缩放、
    F11 全屏等快捷键随 role 注册）+ `autoHideMenuBar` 收起传统栏 +
    IPC `app:popup-menu`（`Menu.getApplicationMenu().popup()`）——
    Renderer 顶栏轻量 ☰ 按钮弹同一份菜单，功能与快捷键一份不少。
  - 顶栏 52px → **44px**；`data-mac` 改为 `data-platform`（mac/windows/other）；
    画布工作区的 canvas-topbar（隐藏全局顶栏后它就是窗口顶栏）同步 44px +
    平台留白，修掉残留的 88px 红绿灯占位。
  - 新增 `shared/platform.ts` 统一平台判定；TopBar/CanvasPage 共用。
- **验证**：系统级截屏（CopyFromScreen，Playwright 拍不到 WCO 合成层）
  确认原生三键与顶栏同底色融合、最大化变还原键无错位；隔离实例实测
  topbar 44.0px / padding-right 137.4px / bar=drag / search+menu=no-drag；
  新增 `tests/e2e/app-shell.e2e.spec.ts` 3 条（44px+拖动分区、Windows 安全区+
  菜单入口、画布顶条同规格）。全量：unit **473/15**；e2e **41 passed / 6 skipped /
  3 failed**（browser 浮点、mcp Windows、settings 路径分隔符为既有问题）。
- **未验证**：macOS（本机无 mac，hiddenInset 配置未动属低风险）与真实
  Linux 桌面环境；全屏（F11）只在 Windows 上经 role 验证了通道。
- **未提交 Git**（与 Phase 1.2、数据目录改动同在工作区）。

## Windows 图标修复（2026-11-12 凌晨）

- 用户反馈：系统弹窗/任务栏显示 Electron 默认原子图标。根因：dev 态
  BrowserWindow 没设 `icon`，也没 `app.setAppUserModelId`（打包版由
  electron-builder 烧进 exe，所以只有开发态露馅）。
- 修复：`window.ts` 非 mac 时按平台选 `build/icon.ico`（Windows）/`.png`
  作为窗口 icon；`index.ts` bootstrap 里 `app.setAppUserModelId('com.brewphase.desktop')`
  （与 electron-builder appId 一致，管任务栏分组与通知身份）。
- 验证：typecheck/build 通过；`getAppUserModelId` 在 Electron 45 无 getter
  （只有 setter），无法程序化读回；沙箱内 OS 截屏管道不可靠（DPI/多屏），
  任务栏图标留待用户肉眼确认——机制是 Electron 文档化的标准做法。


## iOS ↔ Desktop 同步专项测试（2026-11-12 晚）

- 交付：`docs/testing/IOS_DESKTOP_SYNC_TEST_REPORT.md`（本轮只测不改生产码，
  未碰真实库、未执行 wipe）。新增 `Desktop/tests/integration/sync-special.test.ts`（19）、
  `tests/integration/support/sync-harness.ts`、`BrewPhaseTests/SyncSpecialTests.swift`（11）、
  `SyncCrossEndTests.swift`（3）。
- 结果：Desktop typecheck/build 通过、Vitest **507/507**（37 文件）；iOS 全量
  **716/716**（0 failures）；E2E **40 passed / 7 skipped / 3 failed**（3 条均为
  既有 chrome 扩展目录 null、data-location 迁移提示未出现，非同步回归）。
- **真实缺陷 1（P2）**：跨语言负零归一不一致。Swift `%.6f` → `"-0"`，TS → `"0"`。
  跨端实测 `replay conflicts=1 skipped=4 drifted=["canvasNode"]`，即
  `positionX=-1e-7` 的节点永久假冲突，裁决也无法收敛。修法：Swift 侧把
  `|v|<5e-7` 折成 `"0"` 并加 TS 同输入金标（两端只能选一个方向）。
- **真实缺陷 2（P2）**：Record 的 `ON DELETE CASCADE` 绕过 `applyDeletion`，
  不清 `canvasNode` 基线 → iOS 改节点后每轮 `FOREIGN KEY constraint failed`，
  baseline 残留 1 条，无法自愈。
- **P3 边界**：基线丢失重推会复活已删记录（协议允许，需 tombstone）；单条删除
  不清理媒体（孤儿文件，wipe 才清）；重复扫码配对不撤销旧 token（两条同名设备、
  两个 token 均有效）。
- 夹具经验：`test-without-building` 每次重装换容器 UUID，凭据必须**持续广播**到
  所有模拟器 `Documents/sync-harness.json`；跑完要 `pkill -f sync-harness.ts`，
  否则残留指向死端口的夹具文件会让下轮连不上而非 skip。
- 测试自身修正：负零用例 `first.applied` 误抄全实体用例的 8（实际 seed 5 条）。
