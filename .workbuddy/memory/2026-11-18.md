## Remote MCP Phase 1.1B.1：协议与安全边界收口（已实现，未提交）

* **新增 Spike（真实 Electron 45.2.3 主进程）**：`net.WebSocket(url, {headers, protocols})`
  真的把自定义头与子协议送达（服务端收到完整 `Bearer`）；TLS 失败时服务端**连头都收不到**
  → 不存在明文送 token 的窗口。**全局 `WebSocket` 不能设自定义头**，所以生产必须用
  `net.WebSocket`，且拿不到时 fail-closed（绝不静默退回全局——那会让认证在测试里等于没做）。
  服务端发起 4xxx close code 需**完整关闭握手**才精确到达（发完 close 帧立刻 end() 会变 1006）。
* **七个缺陷（1.1B 交付时测试全绿但都没实现）**：
  1. `connect(url)` 丢弃 headers → device_token 根本没发出去；Mock 无条件 101。
  2. 用户绑定检查只在 `start()` 一个分支 → enable/resume/重连都绕过（A 的身份被 B 用）。
  3. `writeAudit` 内部 catch → Remote 审计失败永远记成成功，告警恒为 0。
  4. 帧大小用 `data.length`（字符数），中文少算 2/3。
  5. deadline 每次比较都调 `Date.now()`。
  6. `hello` 字段文档/代码各缺一半（文档有区间、代码有 serviceable）。
  7. 连接尝试的 setTimeout 未清、心跳等第一条 ping、`close(code,reason)` 参数丢、draining 不拒请求。
* **统一解**：`canConnect()` 七条判据成唯一门禁（五条入口全走、`connect()` 内再查一次）；
  `identityGate()` 与 `canConnect()` 拆开——`enable()` 必须先过身份门禁再落盘
  `enabled=true`，否则并发 enable 会写出「开着 + blocked」（测试真抓到）。
* **签名契约**：`helloSigningPayload` 改成签**除 sig 外全部 11 字段**，首行域分隔

* **主动断开必须自己收敛**：传输层刻意让本地 `close()` 不触发 `onClose`（自己的意志不算
  对端异常），代价是心跳超时/握手超时/帧超限都会停在 `online`。新增 `dropConnection()`。

## Phase 1.1B.1 收尾：协议 §2.2 的三条「必须回话」

1.1B.1 主体交付后又补了一批——都是**协议 §2.2 明写、代码没照做**的规则：

* `req` 形状非法（未知键/类型错/缺字段）但 `id` 可读 → 回 `PROTOCOL_VIOLATION`
  （原来静默 return，Cloud 只能等到 deadline，且拿到的是**可重试**的超时码，
  会诱导 AI 重试一个坏帧）。不执行、不写缓存、不改授权状态。
* 非 JSON 帧但能捞出 `req` 的 `id` → 也回话。判据保守：原文含 `"type":"req"`
  且 `id` 出现在 `arguments`/`tool` **之前**。捞不出 → close 4009。
* `hello_ok` 形状错 → close **4009**，版本错才是 **4002**（原来一律 4002，
  于是「Cloud 发畸形帧」被记成版本问题，排障方向从一开始就是错的）。
* 畸形 `grant_update` → 仍要 ack `applied=false, reason:'protocol_violation'`。
  **这条最要紧**：不 ack 会触发 Cloud 的 ack 超时 fail-closed → 暂停该设备
  **全部 grant**，一个序列化 bug 就能让整台设备停服。且绝不部分修改状态
  （测试断言被拒绝的 revoke 不会误清该 grant 的缓存）。
* 畸形 req 的审计口径：`tool` 属于 `REMOTE_TOOLS` 时记 1 行
  （`PROTOCOL_VIOLATION`），工具名不可信则**不记**——`tool_name` 有语义，
  宁可少一行也不用不可信数据污染审计表。
* Mock 新增 `sendText()`（发原始非 JSON）与 `malformedHelloOk` 选项；
  否则 `send()` 总是 JSON.stringify，测不到这两条分支。

**一个没改的地方（有意）**：`dropConnection` 在 `idle` 下会做 `idle → backoff`
非法转换并被静默忽略。核对了全部调用点，都只在 online/connecting/handshaking
触发，该路径不可达；强行加例外会破坏 ALLOWED 表「捕捉非法跳转」的用途。

## Remote MCP Phase 1.2A：Cloud 设备注册与管理（已实现，已推送）

* **前置修了一处真 bug**：`request-handler.ts` 的 `expiresAtMono = startedMono + remaining`
  用了**入口**的 monotonic 去加**之后**才读到的 remaining，等于悄悄扣掉准入检查耗时，
  期限被不可预测地缩短。改为 `deps.nowMono() + remaining`（换算那一刻）。
  新增用例：让前置检查"花掉"500ms，断言结果仍照常发出（旧实现会误判 expired）。
* **迁移**：drizzle-kit 生成 `0001_remote_mcp_devices`，只建两表，**不动六张旧表**。
  迁移测试用**真实基线比对**：只应用 0000 → 快照六表 → 再应用 0001 → 再快照 → 逐字相等。
  （手写「期望结构」等于把测试写成自己的答案，改了旧表也可能因抄对新值而绿。）
* **`mcp_devices`**：`confirm_attempts` 是新增列（文档没有，但 6 位码只有 10^6 空间，
  没有原子计数就能被穷举）。确认码错误的 +1 与「是否越线」放在**同一条 UPDATE**，
  SET 表达式都读旧值 → 无「两个请求都读到 4」的窗口。
* **`mcp_grants`**：与 devices **无外键、互不级联**（grant 属 user）。测试断言
  「撤销设备后 grant 仍在且未撤销」「删 user 时两者都级联」。
* **契约缺口两处（回写协议 §3.3/§3.4）**：
  1. pending 领取必须回 **202** 而不是 4xx——Desktop 轮询把 4xx 当终态，
     回 4xx 会让正常注册在第一次轮询就死。原文只写「否则 409」。
  2. 「已 active 再确认」原文同一格既写 409 又写 200（自相矛盾），取**幂等 200**。
* **顺序不可交换**：claim 校验必须在状态判断**之前**，否则「claim 错」与
  「状态不对」同一个错误 = 白送一个 claim 正确性探针。
* **Cloud→Desktop 接入**：`AccountService.accessToken()` → `DeviceRegistrar` →
  `RemoteService`，单向。registrar 用**工厂**注入（`(origin) => registrar`），
  保证注册与连接用同一个 origin，不会「注册到 A、连 B」。
  token 每次请求现取、不缓存；refresh token 从不流经 Remote。
* **账户切换的竞态**：`claimOnce` 在 await 之后**再查一次 currentUserId**（原来只查
  对象引用），落盘前再查一次。测试用「卡住的 claim」把窗口撑开真的测到。
* 测试：Cloud **161 → 224**（+63，5 个新文件）；Desktop **1194 → 1209**（+15）。
  typecheck / build / mcp:build 全过，`stdio.mjs` 890.30 kB **未变**。

## Remote MCP Phase 1.2B.1.2：握手生命周期与准入并发收口（已实现，已推送）

* **P1 幽灵路由**：`closed` 一个布尔同时表达「socket 没了」和「路由已清」。
  握手在 `verifyHandshake` 的 await 里被 close 打断时，`userId` 还是空串→
  `onClosed` 不解绑并置 `closed=true`；握手恢复后 bind，`sendJson` 失败再调
  `onClosed` → **被幂等闸门挡住直接 return** → 表里留下指向死 socket 的路由。
  修法：拆成 `closing` / `bound` / `released` 三个事实，`releaseRoute()` 独立于
  `converge()` 的 memoized promise——迟到 bind 只能由 **binder 自己**清理。
* **P2 撤停与握手抢跑**：`verifyHandshake` 的 device 是**快照**。suspend/revoke
  提交后 `disconnectDevice` 查 registry 查不到（还没 bind），握手随后 bind
  → 已撤销设备重新上线。修法：`admission.ts` 用 `SELECT ... FOR UPDATE` +
  **锁内 bind**，COMMIT 是线性化点。
* **为什么选行锁而不是进程内 mutex**：`UPDATE mcp_devices SET status` 自动持行锁，
  写路径**无法绕过**；mutex 需要每条写路径都记得参与，漏一处就是静默回归。
  行锁把「必须参与互斥」从约定变成数据库事实。
* **测试不能用 setTimeout**：用可控 Deferred 在精确 await 边界暂停。行锁的判据是
  `pg_stat_activity` 里出现 `wait_event_type='Lock'`（数据库自己的状态），
  拿不到就是互斥不存在——不是「这次没碰上」。
* **变异验证**（8 个变异，7 个被抓）：迟到 bind 不清理→T9、去 FOR UPDATE→T7/T8、

  兜底，行为等价。如实记录，不假装被测到。

  `bindCalls` 结构断言；② `waitFor(count===0)` 在 bind 前就已成立 → 改为等
  `unbindCalls`；③ 断言跑在协程恢复之前 → 加 `awaitHandshakes()`。

## Remote MCP Phase 1.2B.2.1：设备凭据轮换与 rotating（已实现，未提交）

* **upgrade 是无状态的**：`/device-link` 不在 Upgrade 阶段查库（1.2B.1 的决定），
  所以「旧 token 已失效」的表现是 **101 → hello → close 4001**，不是 HTTP 401。
  联调脚本第一版把判据写成 `ok === false` 就假红了——这条对排障有用：
  看到 101 不等于 token 有效。
* **`rotating` 是连接级状态，不是设备状态**。设备轮换后可以立刻用新凭据握手，
  所以把它塞进 `mcp_devices.status` 会让「能不能握手」和「旧连接能不能被路由」
  共用一个字段。`lookup()` 返回 null、`lookupByDevice()` 仍返回——两个问题必须分开答。
* **4010 有歧义，必须按阶段判**：`rotationPhase: 'requesting' | 'reconnecting'`。
  只看「有没有轮换任务在跑」会把「重连后又被人换了」当成「自己那次换完了」吞掉，
  结果是 socket 已死、状态停在 connecting、没有定时器，连接永久假死。
* **新 token 只在响应里出现一次**：落盘必须早于「换内存／重连」。落盘失败只能
  blocked——旧 token 已作废、新 token 已丢，两条路都堵死。这是 fail-closed 的典型形态。
* **网络错误 ≠ 失败**：Cloud 可能已提交。拿旧 token 重试必然 401，会把「未知」
  变成「确定失败」。所以 network 单独归类，直接 blocked。
* **Desktop 测试的时序陷阱**：用「已逾期」的 token 会让 `online` 钩子立刻发起轮换，
  测试去 `waitFor(online)` 就是追一个几毫秒的瞬态，随机器快慢飘。改成
  `tokenExpiresAt = now + LEAD + 400ms`（先在线、再进窗口、显式触发），时序变成单向。
* **假 registrar 必须真提交**：只回 200 的话 Mock 不认新 token，重连必然 401，
  失败点会落在与被测逻辑无关的地方。给 fake 加 `commit` 回调更新 Mock 的设备表。
* 变异验证 7 个，5 个被抓（落盘失败/network/单飞/错钥匙/不落 expiresAt）；
  **两个未被抓**：落盘后复查账户、4010 按阶段区分——都是防御性加固，窗口极窄，
  如实记录不假装测到。
* 测试：Cloud **393 → 432**（+39）；Desktop **1219 → 1245**（+26）。

  + 日志无明文 token）。本阶段**无迁移**。

## Remote MCP Phase 1.2B.2.2：请求转发与 Grant 在线同步（已实现，未推送）

* **准入必须查两张表**。`mcp_grants` 与 `mcp_devices` 没有外键相连，归属关系只能
  逐次核对。只查 grant 会漏「A 的身份 + B 的设备」；只查 device 会漏「B 的 token + A 的 grant」。
  测试里有个专门的变体：**直接改库把 device.user_id 改成别人**——只查 grant 的
  实现会放过它。
* **`lookupByUser` 不判 rotating，`lookup` 判**。轮换时 `rotateConnection` 会
  `unbind`，之后连 `lookupByUser` 也是 null → 派发会答 `DEVICE_OFFLINE`（可重试），
  而正确答复是不可重试的 `DEVICE_UNAUTHORIZED`。修法：转发层自己留
  `ConnSync.rotating`（`onConnectionRotating`），在 lookup 为空时区分两者。
* **排队项不占计数**。占了就等于「凭空多一个在途」，设备明明空闲却报 DEVICE_BUSY。
  `promote` 转 sent 时才 +1。
* **每次 settle 都要 pump 队列**。漏一处，释放出来的槽位要等下一条请求完成，
  队列会一直停泊到排队预算超时。
* **ack 结论不能是布尔**：`applied=false`（对端明确拒绝，要告警）与 ack 超时
  （对端没说话）是两种故障，合成一个布尔时表现为「超时被判成 rejected」。
  用 `'applied' | 'rejected' | 'timeout' | 'offline'`。
* **`hello_ok.grants` 是握手那一刻的快照**：测试里若在 `goOnline` 之后再
  `seedGrant`，那条 grant 不在快照里，断言会在「根本没装」上假绿。三条测试
  第一版就是这么写错的。
* **`installGrant` 对已装的 grant 会先卸旧 ctx**（否则 Desktop 上下文表里会有
  两个 ctx 指向同一 grant_id）。测试里的 `installWithAck` 因此只适用于
  「握手后才新增」的 grant——对快照里已有的会多发一条 revoke 帧。
* **`serialize` 的链尾清理**：存进 Map 的必须是「与 task 同生命周期且永不拒绝」
  的 promise，且清理要判 `chains.get === guard`，否则会把后来者的任务抹掉。
* 变异验证 12 个，10 个被抓。两个不可观测：① `settle` 幂等的返回值（`released`
  标志已提供真实保护，返回值只影响日志）；② `res` 的 connectionId 守卫
  （断线总是先结算，所以迟到 res 走的是「未知 id」分支）——如实记录。
* 测试：Cloud **432 → 530**（+98）；Desktop **1245 → 1265**（+20）。
  构建产物联调 15/15（`dist/` + 真 Postgres + 真 ws）。本阶段**无迁移**。

## 1.2B.2.2-R1：派发/撤销/取消的窗口内竞态（已交付）

- **线性化点是 `reserve()`，不是最终核对**。`revokeInstalled` 的
  `rejectByGrantCtx` 只能看见已登记的请求；先 `lookup` 后 `reserve` 会留下
  「撤销看着空集合顺利完成、随后派发带着已撤销 ctx 写出 req」的窗口。
  条理：准入 → ctx 核对 → 预算 → **reserve** → await 最终核对 → 写 req。
- **rotating ≠ offline**：`registry.lookup()` 对 rotating 返回 null，
  「null ⇒ DEVICE_OFFLINE」会把凭据作废报成可重试。判据用 `ConnSync.rotating`
  （`onConnectionRotating` 里同步置起，早于 markRotating/unbind/close）。
- **`state === 'sent'` 不等于「帧已写出」**：`reserve` 返回 admitted 时就是 sent。
  新增内部事实 `frameSent`，`cancel` 只发给真的收到过 req 的请求（超时与取消
  共用这条判据）。`sendEntry` 首行判 `settled`。
- **重复 install 只有 `applied` / `not_installed` 能继续**。`rejected` 之后继续装，
  新 slot 的 ack 会把 `installed` 置回 true → 在 `syncLag=true` 下重新路由，
  而 syncLag 只该由重新握手清除。三失败各自返回值 + 各自日志事件。
- **写测试时的假绿**：断言「req 帧计数没变」会跑在 `ws.send` 到达之前。修法是用
  「参数带标记的第二次往返」当投递屏障（同一 socket 先写先到），不用 sleep。
- **确定性竞态的零侵入手法**：在测试里包一层 `ConnectionRegistry.lookup` 停在
  Deferred 上，比在 Forwarder 里埋测试钩子更好——钩子的调用位置本身会变成被测行为。
- 变异验证：把 `cloud/src` stash 回修复前，6 条新用例失败（轮换那条实际返回
  `DEVICE_OFFLINE/retryable=true`）；修复后全绿。构建产物联调 26/26，
  同一脚本在修复前构建上第一个判别点即失败。

## 1.2B.2.2-R2：syncLag 是连接级发送闸门（已交付）

- **`syncLag` 原来只是入口/最终核对里的一个判断**，而队列项不重新经过它们：
  A 的 `applied=false` 置位后，B 的排队项仍会被下一次 res 触发的 pump 写出去。
  按 ctx 拒绝拦不住（那条属于 B），按连接全拒会改写已写出的请求——两者都不对。
- 修法三处同时成立：`markSyncLag`（唯一赋值点，置位+记因+**立刻**清本连接队列）、
  `rejectQueuedByConnection`（只拒 queued，不归还计数）、`sendEntry/sendGate`
  （写帧前查：settled / conn 在 / 未 rotating / 未 syncLag / ctx 仍是当前映射，**不查库**）。
- `pump()` 必须循环：被闸门拒绝的项释放槽位，单次 promote 用不上那个槽位。
  重入用 `pumping` 标志压平（结算路径自己也会调 pump），否则递归深度=队列长度。
- **`offline` 也要置 syncLag**：帧没写出去 ≠ 对端状态已知。三种原因各自留
  `apply_rejected`/`ack_timeout`/`offline`，另有 `link_grant_sync_lag_set`
  带 `droppedQueued`——它回答「这次 syncLag 有没有真的停住队列」。
- 恢复只有新握手：`onConnectionReady` 新建 ConnSync（syncLag=false），没有清除路径。
- **测试分层**：ack 超时与写失败用 forwarder 级（真 PG + 真 Forwarder + 可控传输），
  因为生产值 ack 3s > 排队预算 2s，任何推到 ack deadline 的 sweep 都会先把排队项
  按 DEVICE_BUSY 结算掉——真 socket 上这条断言会被另一个合法行为抢先兑现。
- 变异 5 个抓 4 个；`sendGate` 的 `!conn` 分支不可达（onConnectionLost 总是先结算）。
  第一版 `sendGate` 的 syncLag 判断也是「存活」的——eager 清队列已覆盖，必须专门
  构造「syncLag 之后才入队」的用例（模拟 R1 那个入口检查与 reserve 之间的窗口）。
- 测试：Cloud **540 → 557**；Desktop 1265 不变。构建产物 25/25，修复前 19/25 且多写一条 req。

- **刷新失败不能自动恢复**：宽限 30s 只避免撤族。做幂等恢复要么服务端暂存明文
  token（违反「只存哈希」），要么宽限内重签（等于给窃取者第二次机会）。v1 选择

- 最小权限的真正闸门是 **consent 页可逐项取消**，不是 401 challenge：
  省略 scope 后客户端会退化为「用 PRM 的 scopes_supported」（仍是 4 个）。
- `tools/list` **不能**要求业务 scope，否则只授 records 的客户端看不到可 step-up
  的工具。
- 修了 1.3.0 自身的一处内部冲突：§6.4 说 401 带全部 scope，与 §5.8.2 矛盾。

## 1.3.1-A：OAuth 数据层 + migration 0003（已交付）

- **`drizzle(sql)` 会改写该 postgres.js 实例的序列化表**：之后往**裸 SQL**
  传 JS `Date` 参数会被当成 `bytea`，报 `Buffer.from(Date)` 的 TypeError
  （`select ${new Date()}::timestamptz` 都挂）。绕法：`.toISOString()` 加
  `::timestamptz`（`bumpGrantEpoch` 早就这么写，不是巧合）。测试助手统一走 `ts()`。
- `sql.array(x)` **必须给第二参（OID）**：省略时 postgres.js 把数组拼成
  `"x,y"` 字符串 → `malformed array literal`。直接传 JS 数组（`${['a','b']}`，
  含空数组）反而正确，`= any(${arr}::text[])` 也能用。
- `array_length('{}',1)` 返回 **NULL**，而 CHECK 遇 NULL 视为通过 —— 数量约束
  必须用 `cardinality`，否则空数组被静默放行。
- 部分唯一索引 `UNIQUE(session_id) WHERE consumed_at IS NULL` 是 refresh 模型的
  **集合级**不变量；`SELECT … FOR UPDATE` 只保护单行，保护不了「只该有一条」。
  Drizzle 写法：`uniqueIndex(...).on(t.sessionId).where(sql`${t.consumedAt} is null`)`，
  drizzle-kit 能正确生成 `WHERE` 谓词并写进 snapshot。
- **`client_id` 三张新表一律不建外键**：`mcp_grants.client_id` 本来就没有，
  权威记录不受约束而新表受约束会误导；CASCADE 会删掉授权历史，RESTRICT 让
  客户端下线无解。用测试锁住「删 client 不影响 sessions/codes」。
- 迁移**不用** `IF NOT EXISTS`：幂等靠 drizzle journal（按 `created_at` 只应用一次），
  IF NOT EXISTS 会把「已存在但结构不一致」当成成功。
- 兼容性测试仍是「自造基线」：只应用 0000–0002 → 快照 8 张表的列/约束/索引 →
  应用全部 → 逐字比对。比手写期望结构可靠。
- 变异 5/5 全被抓（部分唯一索引、grant 级联、cardinality、公共客户端 CHECK、
  绝对期限 CHECK）。做完必须逐条恢复并用 `pg_constraint`/`pg_indexes` 复核。
- 文档修正：Cookie `Path` 由 `/mcp` 收窄为 `/mcp/oauth`（Path 是前缀匹配，
  `/mcp` 会把授权 Cookie 送到数据端点），consent 随之挪到 `/mcp/oauth/consent`，
  两处必须同时改，否则浏览器不带 Cookie。

## 1.3.1-B：Refresh Token 与 Session 生命周期（已交付）

- **两层模型的运行时不是「代码风格问题」，是两条不变量**：`created_at` /
  `absolute_expires_at` 只在 INSERT 写一次；`sid` 跨刷新不变。任何一次「顺手
  UPDATE 绝对期限」都会退化成 1.3.0 的无限续命缺陷。
- **锁序必须是「先 refresh 行、后 session 行」**。反序会让两个并发刷新各自
  持有 session 锁再互等对方 refresh 锁 → 死锁。宽限判定分支也要守同一顺序。
- **撤销必须事务内返回结论、提交后再抛错**。在事务内直接抛 `invalid_grant`
  会把「检测到盗用」的撤销一起回滚——那等于安全事件没有后果。
- **`eq(col, null)` 永远匹配不到行**，撤销的幂等条件必须写 `isNull(col)`。
- **宽限窗口的测试要推进时钟**：轮换与重放发生在同一毫秒时 `sinceConsumedMs=0`，
  把窗口改成 0 也能通过（变异验证抓到了这个假绿）。改成 +5s 后立刻变红。
- **A8 静态扫描要先剥注释**：源码里本来就有 `absolute_expires_at = created_at + 90d`
  这种说明性注释，不剥掉会让测试永远红——永远红的测试等于没有测试。
- 设计文档 §9.9 的 A1/A3 数字与 30 天 token TTL 不自洽（A1 少算初始那一代；
  A3 的 +31d 必然先撞 token 过期）。已在文档中修正为 6 条 / 29-58-87-89 天，
  语义不变。**照抄会写出永远无法通过的期望，然后为了「通过」去放宽 TTL。**
- 审计事件**不复用** Desktop 的 `refresh_success` / `session_revoked`：前者在
  报表里是「Desktop 登录活跃度」，后者用的是 `auth_sessions.id` 空间。新增
  5 个 `mcp_*` 类型即可（`event_type` 是 text 无 CHECK，加取值不用迁移）。
- `client_id` / `resource` 不由调用方传入，直接从 Grant 取 —— 把「一致性」
  从「需要校验的规则」变成「不可能违反的结构」。
- 变异 9/9 全被抓。基线：Cloud 599 → **643**（+44）；Desktop 1265 不变。

## 1.3.1-C1：Access Token + 浏览器 Cookie + Grant 竞态（已交付）

- **Grant 竞态的形状**：A 读到 `revoked_at IS NULL` → B 撤 grant + 撤会话 + 提交
  → A 才 INSERT session。结果是「撤销完成之后又长出一条有效 Session」，而那次
  撤销事务已跑完，**永远扫不到未来才插入的行**。修法：`createMcpSession` 的
  grant 读取加 `.for("update")`。锁序恒为「grant 行 → session 行」。
- **并发测试要用 `pg_blocking_pids()` 当判据**，别用 sleep：`select 1 from
  pg_stat_activity where <pid> = any(pg_blocking_pids(pid))` 把「确实有人在等
  这把锁」变成可观测事实。移除 FOR UPDATE 后它会超时，失败原因直指问题。
- **失败时的 finally 释锁**：并发用例里若断言失败而把持锁事务留在打开状态，
  后续所有 `truncate` 都会等那把锁，失败会级联成一串 hook 超时，真正的错误
  被淹没。所有持锁/闸门必须 `try { await 判据 } finally { release(); await tx }`。
- **JWT 测试的时钟坑**：`jwtVerify` 用**真实时钟**判 `exp`。把测试基准写成
  固定过去日期（如 `2026-03-01`）会让每条用例死于 `JWTExpired`，看起来像实现
  坏了。用「当前时刻截到整秒」——既可预测又真的有效。
- **Hono 签名 Cookie 的形态**：`<百分号编码的明文>.<签名>`。明文是 JSON，里面
  可能含点号，所以解析要按**最后一个** `.` 切，且先 `decodeURIComponent`，
  不要 base64 解码。
- `deleteCookie` **不会自动带 HttpOnly**，要显式传（浏览器按 name+path+domain
  匹配删除，功能上无差别，但输出头保持一致才不会让审计误判）。
- **`MCP_BROWSER_SESSION_KEY` 刻意不参与启动断言**：Cloud 同时服务 Desktop
  登录，设成必填会让「只跑 /oauth/* 的部署」因为尚未启用的 MCP 能力起不来。
  fail-closed 该放在**能力边界**（C2 缺密钥就不注册 /mcp/oauth/* 路由）。
- 两套 token 共用 `JwtKeyRing`，隔离靠 `aud` 强制校验。测试要加「同 sub 同 sid」
  的同位对照，否则无法排除「因为 claims 不同才失败」。
- 变异 15/15 全被抓。基线：Cloud 643 → **697**（+54）；Desktop 1265 不变。

## 1.3.1-C2a：authorize / login / provider callback（已交付）

- **启用边界要放在「能力」而不是「进程」**：`MCP_BROWSER_SESSION_KEY` 不合格时
  `/mcp/oauth/*` 根本不注册（404），而 `/oauth/*`、`/auth/*`、`/mcp-devices/*`
  照常。把密钥设成 loadEnv 必填会让「只跑 Desktop 登录的部署」因为一个未启用的
  能力起不来——新功能的门禁变成旧功能的故障。
- **三条一次性语义都靠条件 UPDATE**，不是「先查后写」：TOFU 绑定（`IS NULL`）、
  占用 Provider（`provider IS NULL OR provider = $same`）、消费 State
  （`provider_consumed_at IS NULL`）。
- **Nonce 的哈希不能加域前缀**：Google 适配器算的是 `sha256Hex(idToken.nonce)`，
  加前缀会让所有 Google 登录失败，且表现为「登录总是失败」很难定位。
  Provider State 的哈希同理用裸 sha256（输入是 32 字节随机值，不需要域分隔）。
- **Mock 适配器必须校验契约**，否则它只是在验证我自己的拼接：Google 断言
  `expectedNonceHash === sha256(发给 Google 的 nonce)`，GitHub 断言为空串。
- **两处变异一开始存活**（去掉 State 消费的 `isNull`、去掉读阶段 provider 检查）：
  因为它们各有第二道防护，路由层的 400 区分不出来。修法不是删掉纵深防御，
  而是加业务层测试——① 断言内部 `reason`（`provider_mismatch` vs `consumed`）；
  ② 外部事务持行锁，让**两条并发 UPDATE 都阻塞**，从而必然都读到「未消费」，
  提交后只有条件 UPDATE 能让其中一个失败。
- **`pg_blocking_pids(pid) = holder` 只能数到 1**：行锁队列里第二个等待者的
  直接阻塞者可能是前一个等待者。要统计「有几个后端在等锁」得用
  `wait_event_type = 'Lock'`。
- **`c.req.param()` 类型是 `string`，但 Hono 的 `:provider` 可能给出 undefined**
  （TS 报 `string | undefined`），要 `?? ""` 再判。
- 登录页：纯静态 HTML、无脚本、无外部资源、所有动态内容走 `escapeHtml`，
  外加 `no-store` / `no-referrer` / `X-Frame-Options: DENY` / CSP `default-src 'none'`。
- **别同时跑两个 vitest 进程**：它们共用同一个测试库，`truncate` 会互相清数据，
  表现为几十条毫不相关的失败。我踩过一次，误以为是跨文件污染。
- 基线：Cloud 697 → **795**（+98，49 files）；Desktop 1265 不变。
