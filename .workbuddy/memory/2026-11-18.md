## Remote MCP Phase 0：P0-1 / P0-2 设计修订（用户要求，未提交）

* **P0-1 Grant 授权上下文**：A 方案（Cloud 经已认证 WSS 下发上下文）胜出，B 方案
  「每请求签名断言」被否——WSS 已双向认证，签名解决不了撤销，而撤销才是难点。
  `hello_ok.scopes` / `req.grant_id|client_id|client_name` **全部删除**（避免第二个事实来源）；
  改为 `hello_ok.grant_epoch + grants[]` / `req.grant_ctx`（必填）/ `grant_update`+`ack`；
  缓存键 `(grant_ctx, delivery_id)`；撤销 = 先停路由 → `grant_epoch+1` → `grant_update`
  → Desktop 清上下文+该 grant 缓存 → 在途回 `GRANT_REVOKED` → ack；ack 超时 fail-closed
  （暂停该设备全部 grant，协议 §6.5.2 规则 3）。权威：安全 §2.7 / 协议 §6.5。
* **两个 epoch 别混**：`grant_epoch` 设备级（帧新旧门槛，`<=当前` 丢弃）；
  `grants[].epoch` 单 grant 版本（准入第 4 步校验的是它）。
* **P0-2 `jti`**：**Token 级**，v1 不做请求级去重、不加 per-request nonce（按 jti 去重 =
  打死同一 token 的第二次正常调用 = DoS）。旧措辞（安全运维 §5.3「5 分钟重复即拒绝」、
  安全 §1 信任边界「jti + 服务端去重」）已清除。写工具开放前重评 → OQ-16（DPoP）。
* 契约计数：错误码 17→**19**、ST 17→**26**（1.1B 认领 ST-4~10/13~24，1.3 认领 ST-25/26，
  1.2 认领 ST-1~3/11/12）、OQ 22→**23**（+OQ-16；字母组 E 拆 E1/E2 故为 7 项）、
  准入链 8→**12** 步（§8.5 只列前 10）、重连清理 7→**8** 项。

## Remote MCP Phase 1.1B.1：协议与安全边界收口（已实现，未提交）

* **新增 Spike（真实 Electron 45.2.3 主进程）**：`net.WebSocket(url, {headers, protocols})`
  真的把自定义头与子协议送达（服务端收到完整 `Bearer`）；TLS 失败时服务端**连头都收不到**
  → 不存在明文送 token 的窗口。**全局 `WebSocket` 不能设自定义头**，所以生产必须用
  `net.WebSocket`，且拿不到时 fail-closed（绝不静默退回全局——那会让认证在测试里等于没做）。
  服务端发起 4xxx close code 需**完整关闭握手**才精确到达（发完 close 帧立刻 end() 会变 1006）。
* **七个缺陷（1.1B 交付时测试全绿但都没实现）**：
  1. `connect(url)` 丢弃 headers → device_token 根本没发出去；Mock 无条件 101。
  2. 用户绑定检查只在 `start()` 一个分支 → enable/resume/重连都绕过（A 的身份被 B 用）。
  3. `writeAudit` 内部 catch → Remote 审计失败永远记成成功，告警恒为 0。
  4. 帧大小用 `data.length`（字符数），中文少算 2/3。
  5. deadline 每次比较都调 `Date.now()`。
  6. `hello` 字段文档/代码各缺一半（文档有区间、代码有 serviceable）。
  7. 连接尝试的 setTimeout 未清、心跳等第一条 ping、`close(code,reason)` 参数丢、draining 不拒请求。
* **统一解**：`canConnect()` 七条判据成唯一门禁（五条入口全走、`connect()` 内再查一次）；
  `identityGate()` 与 `canConnect()` 拆开——`enable()` 必须先过身份门禁再落盘
  `enabled=true`，否则并发 enable 会写出「开着 + blocked」（测试真抓到）。
* **签名契约**：`helloSigningPayload` 改成签**除 sig 外全部 11 字段**，首行域分隔
  `brewphase.remote.hello.v1`（防跨协议签名复用），字段值含换行则拒绝（防规范歧义）。
  契约/文档/构造/签名四处字段集由脚本逐项比对，实测完全一致。
* **主动断开必须自己收敛**：传输层刻意让本地 `close()` 不触发 `onClose`（自己的意志不算
  对端异常），代价是心跳超时/握手超时/帧超限都会停在 `online`。新增 `dropConnection()`。
* **审计判据**：`audit-log.ts` 拆 `writeAuditResult`（失败抛出，成功要求 `changes===1`），
  旧 `writeAudit` 零改动。测试**真 DROP TABLE** 验证（注入假回调只测到 try/catch）。
* **inflight 语义**：文档原写「挂起并共用结果」→ 改为 **v1 拒绝、不排队**（该路径在同步

## Phase 1.1B.1 收尾：协议 §2.2 的三条「必须回话」

1.1B.1 主体交付后又补了一批——都是**协议 §2.2 明写、代码没照做**的规则：

* `req` 形状非法（未知键/类型错/缺字段）但 `id` 可读 → 回 `PROTOCOL_VIOLATION`
  （原来静默 return，Cloud 只能等到 deadline，且拿到的是**可重试**的超时码，
  会诱导 AI 重试一个坏帧）。不执行、不写缓存、不改授权状态。
* 非 JSON 帧但能捞出 `req` 的 `id` → 也回话。判据保守：原文含 `"type":"req"`
  且 `id` 出现在 `arguments`/`tool` **之前**。捞不出 → close 4009。
* `hello_ok` 形状错 → close **4009**，版本错才是 **4002**（原来一律 4002，
  于是「Cloud 发畸形帧」被记成版本问题，排障方向从一开始就是错的）。
* 畸形 `grant_update` → 仍要 ack `applied=false, reason:'protocol_violation'`。
  **这条最要紧**：不 ack 会触发 Cloud 的 ack 超时 fail-closed → 暂停该设备
  **全部 grant**，一个序列化 bug 就能让整台设备停服。且绝不部分修改状态
  （测试断言被拒绝的 revoke 不会误清该 grant 的缓存）。
* 畸形 req 的审计口径：`tool` 属于 `REMOTE_TOOLS` 时记 1 行
  （`PROTOCOL_VIOLATION`），工具名不可信则**不记**——`tool_name` 有语义，
  宁可少一行也不用不可信数据污染审计表。
* Mock 新增 `sendText()`（发原始非 JSON）与 `malformedHelloOk` 选项；
  否则 `send()` 总是 JSON.stringify，测不到这两条分支。

**一个没改的地方（有意）**：`dropConnection` 在 `idle` 下会做 `idle → backoff`
非法转换并被静默忽略。核对了全部调用点，都只在 online/connecting/handshaking
触发，该路径不可达；强行加例外会破坏 ALLOWED 表「捕捉非法跳转」的用途。
