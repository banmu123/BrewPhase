## Desktop：Phase 3.1 Resolver × Sync 数据一致性（大修）

**根因**：`applyResolvedMetadata()` 把抓取结果写进 `records` 的
source_name/author_name/summary/thumbnail_url_string/metadata_status/
repository_*/canonical_url/platform_content_id——这些列**全部参与 iOS ↔ Desktop
的 record 指纹**。于是自动补全 → 本地指纹偏离 → 同样的 iOS 内容再推 =
假冲突；iOS 删除的 expectedFingerprint 也对不上 = 假删除冲突。
复现输出：`second 0 applied / 0 skipped / 1 conflict, reason "desktop has local changes"`。

**修法（字段所有权按存储位置分离，不是从指纹里删字段）**：
- 迁移 005 新建 `record_metadata`（record_id 主键 + FK 级联 + url_string 失效标记）。
  Desktop Resolver **只写这张表**，`records` 的同步列只由 iOS 同步 / 用户编辑写。
- `toRecordItem` 附带 `metadata` 对象；`metadataStatus` 取本地状态优先。
- 展示层（`buildPreview`、记录卡标题、Inspector placeholder）按**记录优先、
  本地派生补空**组装；自动标题只做 placeholder，用户不输入不会被保存成用户数据。
- Inspector 保存改成 **dirty 感知**：没改过的字段回传记录原值。
- `updateRecord`：URL 变化 → 删 `record_metadata` 行并按新 URL 重建 pending；
  载体变非 link → 整行删。
- `snapshot-importer`：iOS 更新记录后 `reconcileRecordMetadata` —— URL/载体变了
  才删本地派生行，否则原样保留（iOS payload 不含本地派生信息也不会清空）。
- **指纹字段列表一个字没改**（两端镜像不动），所以 iOS 端零改动、无需跑 iOS 指纹测试。

**测试**：`tests/integration/sync-metadata.integration.test.ts` 6 大场景（10 条）：
首次同步+补全后重推不冲突、刷新失败不丢数据、iOS 改字段/改 URL、iOS 删除
（含"桌面真改过仍产生删除冲突"）、用户改标题仍冲突、连推三次幂等。
验证：vitest **213/213**、typecheck 双工程、build、E2E 3/3。
真实库副本上跑过迁移 005：表建好、2 条记录完好、0 行回填（有意不回填）。

## Desktop：Phase 3.2 同步后自动补全 + 搜索/详情接入派生元数据

- **ResolveQueue**（`metadata/resolve-queue.ts`）：并发 2、幂等键 `recordId+urlString`、
  失败不重试、`onSettled` 广播 `records:metadata-updated`。执行体**同步启动**
  （`enqueue` 后立刻进入 running），否则测试里 release 打不到 gate。
- **触发点**：`SyncServer` 在 `applyBatch()` 返回（事务已提交）后回调 `onApplied`，
  `index.ts` 只取 `results[]` 里 `entityType=record && status=applied` 的 id →
  `prepareLocalMetadata()` → 需要时入队。**网络永不在事务里**。
  `skipped/conflict/failed` 一律不入队。
- **抓/不抓规则**：无派生行或 URL 变了 → 建 pending + 抓；同 URL `pending` → 抓
  （崩溃恢复）；同 URL `ok/failed` → 不抓（失败只能手动刷新）。
- **启动恢复**：`pendingMetadataJobs()` 扫 `status='pending'` 且 url 与记录一致、
  记录仍是 link 的行；不恢复 failed。
- **搜索**：`listRecords` 用 EXISTS 子查询接入 record_metadata（url 必须一致），
  不用 JOIN（关系不唯一会出现重复行、分页错位）。
- **详情**：`recordDisplayTitle()` + `PreviewInfo` 块（仓库/语言/★/Fork/摘要/封面），
  与卡片共用 `buildPreview`；顶部只显示一次作者/来源（删掉重复的 `LinkMetaLine`）。
  卡片标题顺序改为「用户标题 → 派生标题 → GitHub 身份 → 摘要首行 → 载体名」。
- **E2E 夹具**：`BREWPHASE_METADATA_FIXTURE=1` 让主进程抓取器返回固定 GitHub
  响应（page.route 拦不到主进程请求）；生产不设该变量，安全层强度不变。
- **无新迁移**（沿用 005 的 record_metadata）：239 测试、typecheck、build、E2E 4/4。

## Desktop：Phase 3.2.1 收尾（URL 原始值 / 时序文档 / 调度测试 / 真机矩阵）

- **URL 一致性**：`prepareLocalMetadata` / `seedLocalMetadata` 存进 `record_metadata`
  的 `url_string` 一律用 `records.url_string` 的**原始值**，`trim()` 只用于判空。
  否则 iOS 带空格的 URL 会让派生行、队列任务、`expectedUrl`、`pendingMetadataJobs`
  各持不同字符串 → 永远 pending、元数据不显示、搜索不命中。**不要再 trim 后存储。**
- iOS 侧确认：`RecordEditorView` 保存时走 `Record(...).resolvedLink`（内部 trim）
  再取 `absoluteString`，所以真机 URL 本身是干净的；桌面仍按原始值兜底。
- **时序文档更正**：实际是「applyBatch 提交 → onApplied 同步入队 → 写 200 响应」，
  不是「响应发出后才入队」。入队不发起网络，所以响应延迟与 Resolver 无关。
- **调度接线测试**：`recordIdsToResolve()` 抽出过滤逻辑（只认 record+applied），
  SyncServer 用真实 HTTP 验证：新建→回调收到 id 且数据已提交；重复→skipped 不调度；
  桌面改过→conflict 不调度；Resolver 卡死时 apply 仍 <1s 返回。
- **真机矩阵**：`REAL_DEVICE_SYNC_GUIDE.md` 增加 Phase 3.3（A 首次同步/B URL 生命周期/
  C 幂等冲突/D 异常恢复/E 媒体），附验收记录表模板，**状态标注为未执行**。
- 验证：vitest 248/248、typecheck、build、E2E 4/4。
