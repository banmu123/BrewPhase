# BATCH2_WRITING_SPEC — Batch2 训练候选写作规范（冻结版）

> 日期：2026-10-14 ｜ 依据：GPT 阶段五点九提示词 + Batch1 全流程经验
> （试点审核 / 全量审查 / weak-chalky 修正 / CLAIM_POLICY / 术语冻结）
> **本规范冻结后，Batch2a 候选生成必须逐条遵守；审核阶段将按此逐条验收。**
> 本文件只定义规范，不生成候选数据、不修改已有数据与准入规则。

## 1. 样本定位

训练目标**不是**知识百科问答，而是训练 BrewPhase 专用模型的五种能力：

1. 用户问题理解（从模糊口语还原真实意图）；
2. 风味/萃取诊断（症状 → 多因分析）；
3. 条件分析（设备/烘焙度/配方/豆况对结论的影响）；
4. 限定表达（不确定性、适用范围、来源边界的语言习惯）；
5. 下一步建议（可执行的验证/调整动作）。

**定位句**：构建「具备咖啡诊断思维链和知识边界意识的 BrewPhase 专用模型」——
Batch1 解决知识正确性，Batch2 重点强化诊断能力。

## 2. 问答结构规范

每条候选回答必须包含四段逻辑（可自然行文，不必硬分标题）：

- **A. 直接结论**（先回答问题本身）；
- **B. 原因解释**（为什么）；
- **C. 条件限制**（什么情况下不成立/适用范围）；
- **D. 可执行建议**（下一步怎么做、怎么观察效果）。

**避免**：绝对化答案、单因素解释、伪精确数字（无来源边界的数字）。

## 3. F/P/I 分层规范（承接 CLAIM_POLICY.md）

所有回答的关键句必须可归入三层，且**语言标记不可省略**：

- **F**（source-backed fact）：必须可回溯到具体 `claim_id`/`rule_id` 与来源；
- **P**（expert practice）：必须带「常见做法」「经验上」「很多咖啡师会」类标记；
- **I**（inference）：必须带「可能」「通常意味着」「可以尝试判断」类标记。

**禁止把 I 写成 F。** 审核时逐句核对层级标记（Batch1 的 b1-013 教训）。

## 4. 咖啡诊断类规范（P0 主题专用）

诊断类回答**禁止直接给参数**，必须走完整链路：

```
现象 → 可能原因（多因并列） → 验证方法 → 调整方向
```

示例：用户问「手冲很酸怎么办」——
不能直接「降低酸度/磨细」；应分析：萃取不足？豆子本身明亮酸质？烘焙度？水温？粉水比？
——先分因，再给验证方法（滴滤速度/ TDS / 对比冲煮），最后才是调整方向。

## 5. 数字规范

所有数字（温度/比例/时间/日期/重量）必须：

1. **有来源**（可回溯 claim 或原文核验记录，见 external_evidence_packet.md）；
2. **有适用范围**（什么器具/豆子/语境下成立）；
3. **不表达唯一答案**。

**禁止**：「最佳比例」「黄金时间」「标准温度」类表述（b1-025 的处理方式是范例：
配方=「来源+作者+器具+语境」的组合）。

## 6. 来源规范

来源分四类：官方来源 / 研究来源 / 厂商指南 / 经验资料。

- 厂商建议必须写「某品牌/作者推荐的方法」，**不得转换为「行业标准」**；
- 研究结论必须带实验条件（如 UC Davis 冷萃：Arabica、特定烘焙度与温度组合）；
- 每条候选的 `source_ids`/`claim_ids` 必须真实可回溯，禁止编造 ID
  （构建器会反向校验）。

## 7. 术语规范（冻结，禁止混用）

| 原文 | 用词 | 避免 |
|---|---|---|
| weak | **寡淡**（浓度不足） | 空洞 |
| chalky | **粉感**（粉笔感） | 发涩（作为对应词） |
| astringent | **涩感/收敛感** | 与 chalky 混用 |

用户口语「发涩/空洞」出现时：保留用户语言，用冻结词解释严格含义（term_freeze_decision 策略 B）。

## 8. Batch2 优先主题（对应 batch2_candidate_plan.md）

- **P0**：espresso dial-in、pour-over diagnosis
- **P1**：freshness、recipe interpretation
- **P2**：cold brew、grinding、health、refusal examples

## 9. 候选审核字段要求

Batch2 候选每条必须携带（构建器/审核工具按此验收）：

```
sample_id / messages / topic / claim_ids / source_ids /
reasoning_level(F/P/I 标注说明) / license_status / source_usage / risk_notes
```

## 10. Batch2 与 Batch1 的差异总结

| 维度 | Batch1 | Batch2 |
|---|---|---|
| 重点 | 知识正确性（来源边界、许可、防泄漏基建） | **诊断能力**（思维链 + 条件分析 + 限定表达） |
| 规模 | 30 条候选 → 5 approved | 规划 29–40 条 → 目标 20–40 approved |
| 写作依据 | 逐条从 claim 表转述 | 本规范 + CLAIM_POLICY + 术语冻结 |
| 数字处理 | 部分数字未核验（教训） | 无来源边界的数字一律禁止 |
| 审核强度 | 试点逐句核验起步 | 按本规范逐条验收 + 外部证据包佐证 |

## 11. Batch2a 首轮规模（GPT 建议）

**10 条**（不是一次 40 条）：意式 dial-in 4 + 手冲诊断 4 + 新鲜度 2——
先验证本规范有效，再扩展到 29–40 条。
