## 一、四项必须先解决的问题

### 1. 最终验收集与 E1 阶段闸门存在冲突

涉及：product_eval_v1_spec.md、e1_e2_training_strategy.md

评测规范明确规定 Product Eval v1 只用于正式验收，不能参与基座选择、训练或调参。但 E1 训练策略又规定，E1 的评测包含 Product Eval v1，并以相关门线全部通过作为申请 E2 的条件。

这意味着最终验收集会参与决定后续训练是否继续，与它的独立性约束不一致。

**裁定：必须将阶段验证与最终验收分开。**

| 评测资产 | 允许用途 |
|---|---|
| 30 案例基座开发集 | 三个候选基座的零样本比较、最终选择一个基座 |
| 独立的 E1 阶段验证集 | 判断 E1 决策能力是否达到申请 E2 的门槛 |
| 冻结的 Product Eval v1 | 最终候选的正式产品验收，不反馈给训练决策 |
| C/D 原 20 题回归套件 | 保留历史错误和事实退化检查，并明确各项对应的回归判据 |

E1 的阶段验证应有自己的案例、分母和门线。不能因为 Product Eval 的分数不理想，就再去改变训练配置；也不能因为 E1 需要决定是否进入 E2，就把 Product Eval 变成阶段调试集。

另外，E1 的主要目标是结构化决策 JSON。自然度、正文接续和跳过后回答质量，是端到端产品行为指标，不应直接当作 E1 JSON 生成器的自然度指标。若需要提前检查这些行为，应在单独的阶段验证集上，通过现有 RAG 回答链路进行组合测试。

### 2. 注册表渲染问题与决策 JSON v1 的输出契约不一致

涉及：decision_schema_and_registry.md

这份文件同时定义了两种做法：Schema v1 要求 action="clarify" 时模型输出非空 question 字符串（E1 训练目标也包含此字段）；设计决定又写明问题文本由注册表模板渲染、模型只选变量。两者没有真正对齐——既然要机械保证问题来自注册表，就不应继续用「问题语义是否一致」这种难以可靠自动验证的规则作为主要保障。

**建议：把模型协议与程序生成的问题文本明确分开。** 模型输出精简为决策所需字段：

```json
{
  "schema_version": "2",
  "action": "clarify",
  "missing_variable_id": "grind_size",
  "reason_code": "insufficient_diagnostic_information"
}
```

代码完成校验后，通过 missing_variable_id 从 DecisionVariableRegistry 取得标准问题，再交给 UI 展示。模型不负责生成可展示的问题文本。

**治理要求**：Q1 之前已批准带 question 字段的 Schema v1，采用精简协议必须正式记录为新的 Schema 版本，并保留原裁定和变更理由，不能悄悄修改已批准的契约。

同时补齐跨字段校验：action="answer" 必须对应 reason_code="information_sufficient"，避免字段各自合法、组合起来却自相矛盾。

注册表问题需执行单变量检查：water_hardness 的问题同时问水源类型和硬度，equipment_cleanliness 同时问清洁与除垢——改为每轮只获取一个关键变量，其他信息另开一轮或作可选补充。

### 3. E2 回答训练记录没有完全对应实际调用序列

涉及：e1_e2_training_strategy.md

E-7a 要求每个用户新回合都重新决策；用户补充后决策为 answer，代码才调用正文生成。但当前回答记录模板（首轮问题 → clarify JSON → 用户补充 → 正文）**缺少用户补充后的新一轮 answer 决策 JSON**——训练时正文模型看到的上下文，不一定是推理时真正收到的上下文。

**必须先冻结实际的第二次生成调用契约，再按该契约构造回答记录**：如果正文生成时会把第二次决策 JSON 作为内部上下文，就应当在训练记录中按相同方式呈现；如果实际实现不会传入它，就不要只为了保留决策能力而在训练样本中添加它。

历史追问的展示形式也必须明确：UI 展示的是注册表生成的自然语言问题，而不是内部决策 JSON。训练数据应反映真实对话历史与真实调用输入，不能混淆内部协议消息和用户可见消息。

--mask-prompt 方向合理，但它只解决「哪条消息计损」，不能自动保证该消息的上下文与 App 实际推理一致。

### 4. 变量注册表的部分 claim 锚点存在授权范围问题

涉及：decision_schema_and_registry.md、human_review_rubric.md、source_exceptions.json

不能把「有 claim ID」直接视为「该 claim 已获准用于目标产品的数据和训练用途」。现有例外记录中若干来源明确限定为 noncommercial-research，例如：claim.pourover.v60-official-tuning（Hario）、claim.espresso.fellow-ratio-1to3（Fellow）、claim.freshness.nca-lose-freshness-immediately（NCA）、claim.roasting.ta-sourness-correlation（UC Davis）——这些不能自动授权未来商业产品的训练用途。另外 claim.freshness.light-roast-rest-4-6w 被现有授权说明明确排除在 Fellow 例外范围之外，不能仅因出现在知识文档中就当作已获准事实锚点。

数据生成前必须区分「仅用于设计决策的参考」与「实际进入训练轨迹的事实依据」。对真正进入训练样本的事实，逐条验证 claim 存在、来源证据支持表述、授权覆盖实际训练用途及目标部署用途。若某 claim 仅用于论证「变量为何有诊断意义」而不会注入模型输入或成为训练目标中的事实，应在设计中明示其 **design-only** 身份。

## 二、其余三项文档的审查结果

### ② 基座筛选方案：方向合理，排序规则还需锁定

「误追问率优先」缺最低正确追问率门槛——完全不追问的模型可能凭低误追问率取得较好排序。改为：先满足结构合法率门槛 → 再满足正确追问率和误追问率各自最低要求 → 最后按误追问率、正确追问率和端侧成本**字典序排序**。具体门线在跑分前锁定。Qwen 模型卡（3B=qwen-research，4B/7B=Apache-2.0）与设计包提醒一致；最终仍核验实际下载的量化版本与转换来源。

### ③ 人工审核 rubric：基础扎实，数据模型与执行流程需再对齐

- synthetic_scenario 需机器可查结构：增加 `synthetic_fields` 或逐字段 `is_synthetic`。
- 「AI 初审 + 人工终审」与「双人人工终审」表述不一致：AI 只辅助生成与机器预检，人工审核者独立完成终审；如要求双人终审，须定义两名人工审核者及分歧处理流程，不能把 AI 计作第二名审核人。

### ④ Product Eval v1：框架保留，案例与门线冻结前修正

- 示例案例金标准不一致：「手冲又苦又涩」已告知 brew_method=手冲，不能再列为缺失变量；案例定义要求只预埋一个缺失关键变量。冻结版每案例须明确**唯一目标变量**；若存在多种可接受变量选择，须提前定义允许集合与追问正确性规则。
- 门线写成实际通过数：E-d 8 案例、≥90% ⇒ 实际 8/8 才达标（7/8=87.5% 不够）；结构合法率分母按**实际发生的决策调用**计（正文生成调用目标是自然语言不是 JSON）。
- E-e 需明确独立判据（不能只含在总体结构合法率里）；C/D 回归按具体失败类型设定判据，不用综合行为分替代事实回归检查。

### ⑤ E1/E2 训练策略：分期正确，与新数据结构衔接要明确

- E 的元数据用 trace_id/split_group_id，而现有 validate_data.py、split_dataset.py、check_training_leakage.py 用 sample_id/group_id 及既有字段——**需补「新轨迹模型 → MLX-LM 训练记录 → 现有准入脚本」的字段映射表**，不能只写「按 split_group_id 扩展」。
- 规定：同一 trace_id 的训练记录继承相同 split_group_id；近似轨迹整组同集合；E 数据训练准入用正确部署用途声明；泄漏检查以**最终训练目标消息**为准，而非只比较记录中第一条 assistant 消息。

### ⑦ App 运行方案：架构合理，导出与运行时验收表述需更准确

- 「与训练侧逐位校验」不宜作跨转换、跨推理运行时的通用要求——改用固定测试集上的**行为一致性验收**（Schema 合法率、决策一致率、变量选择一致率、回答质量、延迟、内存）。
- 端侧内存数字只是规划估算：明确目标机型、最大上下文长度、两段式生成负载、峰值内存、P50/P95 延迟，对选定最终模型真机实测。
- Qwen3 的思考模式与输出模板必须在开发集筛选和最终运行时中显式设定一致，否则 JSON 合法率比较会混入不同生成模式的影响。

## 三、方法论参考映射是否恰当？

定位正确（方法论参照非训练代码依赖），映射基本认可。Chapter 6 分类微调可类比有限决策空间，但**分类任务 ≠ 生成式 JSON 决策**，不能直接照搬训练头或评测形式。DPO 保留为远期候选。

建议增补两项参照：① Chapter 7 中指令样本格式、训练/验证划分与训练目标构造的部分；② **直接引用 MLX-LM 官方的 chat 数据、损失掩码与训练文档作为实施规范**——--mask-prompt、实际训练命令及版本约束以 MLX-LM 为准，不依赖教学仓库推断。

## 四、最终处理意见

| 审查项 | 结论 |
|---|---|
| 七件套整体结构与 Q1–Q6/E-7 约束 | 基本通过 |
| Product Eval v1 冻结 | 暂不通过 |
| Schema 与注册表的输出契约 | 须先统一并版本化 |
| E2 回答记录与真实推理上下文 | 须先对齐 |
| 数据事实与授权范围 | 须逐条验证后方可生成训练素材 |
| 新数据与既有准入脚本的衔接 | 须补映射与扩展方案 |
| 进入正式数据生成、基座筛选 | 暂缓 |
| E1/E2 训练 | 仍未批准 |

请先按上述事项形成 v0.2，**保留 v0.1 作为历史版本**，尤其不要把 Schema 契约、授权边界或最终验收集用途的变更静默写入原文件。

最重要的顺序：**先统一协议与评测边界 → 再核验来源授权、修正案例金标准与数据字段 → 最后由负责人冻结 product-eval-v1 并申请启动后续数据准备和基座筛选。**
