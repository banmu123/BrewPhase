## E-7a：E2 推理编排方式

裁定：采用方案②——决策与正文生成解耦，由代码负责编排。

模型调用与产品交互应按以下逻辑执行：

**第一步：决策调用**——模型只输出符合约定 schema 的决策 JSON。代码解析并校验 action、missing_variable_id 等字段。

**第二步：代码编排**——若 action = "clarify"，向用户展示 question 并等待补充；不提前生成最终回答。若用户跳过，则按已定义的跳过路径记录状态。若 action = "answer"，进入回答生成路径。

**第三步：回答调用**——当具备回答条件时，代码将有效对话历史、用户补充信息、适用的 RAG 上下文及必要约束组装为输入，再调用模型生成自然语言正文。正文调用只负责回答，不输出决策 JSON。

**关键区别：这里的「两段式」是决策阶段与回答阶段分开，不是每次追问后立刻连续调用两次模型。** 追问分支必须等待真实的下一轮用户输入；直接回答分支则可在决策通过校验后进入正文生成。

选择方案②的理由与你方提出的基本一致：RAG 注入点明确、决策结果可审计、正文不会污染决策协议，也方便单独统计决策错误与回答错误。

## E-7b：E1 assistant 训练目标序列

裁定：确认。E1 的 assistant 目标序列就是决策 JSON 本身，不包含回答正文，也不额外增加 XML、Markdown 代码围栏或自然语言包裹。

示例：

```json
{
  "schema_version": "1",
  "action": "clarify",
  "missing_variable_id": "grind_size",
  "question": "这杯咖啡的研磨度大概是多少？",
  "reason_code": "insufficient_diagnostic_information"
}
```

当应该直接回答时，目标仍然是决策 JSON，只是 action 为 answer，missing_variable_id 和 question 均为 null。它们不是要求模型在 E1 阶段生成的用户可见答案。

## 对设计包的补充约束（三点必须一并落实）

**1. 每个用户新回合重新决策。** 初次追问之后，收到用户补充或跳过信息时，不能把旧的 clarify 决策直接当成新的 answer 决策。应基于更新后的对话历史再次执行决策调用；通过校验并得到 answer 后，才进入正文生成。这样才能覆盖继续追问、直接接续和跳过路径。

**2. E2 的训练目标要按调用职责分开。** 决策调用的目标仍是 JSON；回答调用的目标是纯自然语言正文。输入模板必须明确当前任务，避免模型把 JSON 混入回答正文，或在决策阶段输出额外解释。设计包还应说明 E2 如何保留 E1 已学会的决策能力，并通过回归评测检查遗忘或退化。

**3. MLX-LM 数据构造必须与目标序列对齐。** 官方文档支持 `{"messages": [...]}` 格式的 chat 数据，并提供 `--mask-prompt`（只对目标 completion 计算损失；启用时最后一条 assistant 消息作为训练目标）。因此每条训练记录必须明确哪条 assistant 消息是本样本的目标。不要简单把完整多轮轨迹放进一条记录就以为模型会同时学习其中所有 assistant 回合。

建议将一条实际追问轨迹关联的样本拆成目标明确的训练记录，并保留共同的轨迹 ID 与分组标识，确保数据划分时整组进入同一个集合，避免近似场景跨集合泄漏。

## 最终执行口径
