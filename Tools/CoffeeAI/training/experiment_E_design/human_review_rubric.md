## 一、轨迹数据模型（Q3 七字段 + 补充）

每条**轨迹**（一个完整交互场景，可含多轮）的最小元数据：

| 字段 | 类型 | 要求 | 机器可查 |
|---|---|---|---|
| `trace_id` | string | 唯一，格式 `e2t-<batch><seq>`（如 `e2t-a001`） | ✅ 唯一性脚本 |
| `behavior_class` | enum | `A`（追问→接续）/ `B`（追问→跳过）/ `C`（直答）/ `D`（特殊防护） | ✅ 枚举校验 |
| `synthetic_scenario` | object | 场景合成属性 + **机器可查的合成标记**：`synthetic_fields: ["method", "symptom"]`（逐字段列出合成项；非合成字段不得列入） | ✅ 字段存在性 + 白名单枚举校验 |
| `claim_ids` | string[] | 助手各轮回答实际使用的已授权 claim；**逐条存在于知识库且来源授权覆盖当前用途** | ✅ 对照知识库脚本 |
| `interaction_skill` | enum | `clarify` / `direct_answer` / `skip_handling` / `boundary`（沿用既有 skill 词汇） | ✅ 枚举校验 |
| `review_status` / `reviewers` / `owner_ruling` | string/array/object | `draft → approved | rejected`；**审核者数组**（v0.3）：`reviewers: [{reviewer, verdict, notes, reviewed_at}]`——两名独立人工审核者各自记录结论与时间；分歧时负责人裁定独立记入 `owner_ruling: {ruler, decision, rationale, ruled_at}`——双人工审核在数据中留可审计证据 | ✅ 状态机 + 数组完整性（approved 须 ≥2 条 reviewer 记录） |
| `split_group_id` | string | **同场景的近似轨迹共组**——数据划分时整组进同一集合（防泄漏，Q3 明确） | ✅ 划分脚本强制 |

**轨迹 → 训练记录的拆分**（E-7 约束③）：一条轨迹按 E-7a 的调用职责拆成多条目标明确的
训练记录（决策调用记录：目标=决策 JSON；回答调用记录：目标=纯正文），全部携带同一
`trace_id` 与 `split_group_id`。

## 二、六检查门（GPT 框架 → 检查项与判据）

### 门 1：来源、claim 与使用目的授权合规

- [ ] `claim_ids` 全部存在于知识库（脚本：对照 `knowledge/` claim 表）
- [ ] 各 claim 的来源授权覆盖**当前用途**（对照 `Tools/CoffeeAI/source_exceptions.json`：allowed_topics 含场景主题；E 数据集用途在来源许可范围内——**样本获批 ≠ 无限制授权**）
- [ ] 场景与 claim 的语境不冲突（如冷萃 claim 不用于意式场景的事实句）
- 机器可查：前两项脚本化；第三项人工。

### 门 2：多轮轨迹完整、接续正确

- [ ] 每轮助手回答基于**更新后的**对话历史（含用户上一轮补充），无复读第一轮
- [ ] clarify 后的用户补充被实际使用（正文引用了补充信息指向的变量）；跳过后走有边界建议路径（B 类）
- [ ] 用户跳过时不得假装用户已回答（E-7 约束①：旧 clarify ≠ 新 answer）
- 人工逐条；脚本可辅助检查「补充变量是否在后续正文出现」。

### 门 3：追问必要性与单问题纪律

- [ ] 追问发生的前提是**信息确实不足以决策**（对照该场景 `synthetic_scenario` 预埋的缺失变量——预埋即金标准）
- [ ] 每轮至多追问**一个**注册表变量（决策 JSON 的 `missing_variable_id` ∈ 注册表 14 项；blocked/design-only 变量按①§2.5.2 准入状态约束场景生成）
- [ ] 不连续追问同一变量两次；不追问用户已提供过的信息
- 机器可查：决策 JSON 对照注册表与场景缺失变量标注；文本自然度人工。

### 门 4：补充/跳过后的响应正确性

- [ ] 用户补充后：决策调用产出 `answer`（或合理的下一个 clarify——若补充后仍缺另一关键变量，且该轨迹预埋为「多变量缺失」）；正文结合补充信息展开
- [ ] 用户跳过/不知道后：给**有边界的条件化建议**（if-then 结构：按常见情况给方向 + 明确「如果你的情况是 X 则相反」），不编造用户信息
- [ ] C 类（信息足够）轨迹**零追问**——防模板化的对照面
- 机器可查：行为分类与轨迹 `behavior_class` 一致；人工：建议质量的边界感。

### 门 5：事实有据、P/I 不冒充 F

- [ ] 所有可核验咖啡事实句能在 `claim_ids` 中找到出处；无 claim 支撑的机理句不得写成事实
- [ ] 实践建议（P）与推断（I）沿用 Batch2e 对称标记惯例：【P】…【/P】、【I】…【/I】包裹实际内容；推断必须有限定词；**成对 + 无残留 + 逐句归属**三层检查（前两层脚本，第三层人工——Batch2e 六轮复核的核心教训）
- [ ] 不编造数字、不把相关性说成因果、不越过来源原意的强度
- 机器可查：标记对称性脚本（沿用 `check_candidate_quality.py` 思路 + 「全 0 不判通过」修复）；claim-grounding 对照脚本（E 数据集专版）；人工：逐句归属。

### 门 6：表达自然、无模板、无隐私泄露、无越界

- [ ] 各轨迹的开场/追问措辞有变化，不出现固定句式复读（与同批其他轨迹比对）
- [ ] 合成用户信息不含真实个人数据（姓名/电话/账号）；`synthetic_scenario` 如引用真实产品型号，仅用知识库已收录型号
- [ ] 无医疗诊断、无「换个豆子就好了」式的无依据断言、健康问题走现行边界话术
- [ ] 语言为简体中文（与产品一致），语域自然、不过度口语化也不过度书面
- 人工逐条 + 抽样脚本（n-gram 重复检测辅助）。

## 三、审核流程

```
AI 辅助生成（场景扩展）→ 机器预检（门 1/3/5 的脚本项）→ 人工终审（六门全过）
  → review_status=approved → 入 E 数据版本 → split（按 split_group_id）→ 准入检查
```

- 机器预检不过的**不进入人工终审**（节约审核精力，也强制生成端质量）。
- **角色定义（v0.2 统一）**：AI 只承担场景生成辅助与机器预检，**不计入审核人数**；
  终审由**两名相互独立的人工审核者**完成（审核者 A 全量终审 + 审核者 B 独立复核；
  两人均不得是该轨迹的生成者）。分歧处理：A/B 结论不一致的轨迹提交负责人裁定，
  裁定结果与理由记入 `review_notes`；裁定案例沉淀为 rubric 补充判例。
- 拒绝样本保留原样（`review_status=rejected` + 原因），供失败模式分析与 rubric 迭代。
